# ADR-0340: Run executor framework

- Status: agent-decided
- Date: 2026-10-09
- Task: T-070
- Affects: LIF-002, LIF-022, LIF-040, LIF-042, LIF-046, DOM-010, JOB-010, JOB-044, JOB-060

## Context

LIF-040 lists the Steps of a Run and LIF-046 the lease, but not how Steps are registered by later tasks, who moves a Run from `queued` to `running`, what a worker may write once it lost the lease, which row locks are taken in which order, how a delayed resume (JOB-044, JOB-015) and a SIGTERM hand-off share one path, what a cancelled Run looks like, or what the executor does about a failing `analyzeForRun` (ADR-0310 named the gap). T-071 to T-073 need a registration API that does not change under them.

## Decision

- **Where.** `packages/jobs/src/run/`: `types.ts` (the vocabulary), `executor.ts` (`executeRun`, `runHandlers`, `createRunAnalysisPort`), `finish.ts`, `guard.ts`, `ledger.ts`, `findings.ts`, `store.ts`, `errors.ts`, `orphans.ts`. The pure ledger rules are in `@git-migrator/core` (`ledger.ts`).
- **Registration.** `RunStepRegistry<S>.register(kind, planner)`, one planner per Run kind. `planner.steps({ run, migration })` returns the ordered `StepDefinition`s: `key`, optional `facetKey`, `severity` (`fatal` | `independent` | `advisory`, ADR-0341), optional `maxAttempts`, and `run(ctx)`. `S` is the process services type (adapters, git, scratch) the worker passes as `ctx.services`, so T-071 injects what it needs without the framework knowing it. The worker owns the registry (`apps/worker/src/worker.ts`); until T-071 registers `migrate`, `run_anyway` and `resync`, a Run of such a kind fails at once with `run.kind_unsupported`. T-071 provides tests with the fakes; this task tests with synthetic Steps.
- **Step rows are identified by key and Facet.** (Round 2.) The unique key is `(run_id, step_key, COALESCE(facet_key, ''))`; a start or a resume inserts the planned Steps that have no row, appending them after the highest `order`, in plan order, and marks a stored unfinished row that the plan no longer contains `skipped` with `{ code: 'run.plan_changed' }`. The Steps run in the order of the current plan, matched to rows by identity. The first version keyed rows by position, so a plan that gained a Step between a start and a resume skipped it and ran a later one twice.
- **LIF-005 at start.** After the inline Analysis, the executor reads the current readiness once more; if `allowedReadiness(kind)` no longer admits it (the Migration became blocked while the Run was queued), the Run ends `cancelled` with `readiness_changed`, before any Step.
- **Starting.** `run.execute` calls `keepRunLease({ startQueued: true })`. `startQueuedRun` is one `UPDATE ... WHERE status = 'queued' AND cancel_requested_at IS NULL` that sets `running`, `started_at` and the lease token, so two jobs cannot both start a Run and a cancelled Run is never started. A claim that fails (another holder, finished Run) returns `not_claimed` and does nothing, which also makes a re-delivered job a no-op.
- **Fence.** Every write of the executor that changes the Run's own state (Step status, findings, the end of the Run) is a transaction whose first statement is `SELECT ... FROM run WHERE id = $1 AND lease_owner = $token AND status = 'running' FOR NO KEY UPDATE`. No row means `RunLeaseLostError`: the worker returns `lost` and stops. The reaper's resume marker, a takeover after expiry and a finished Run all change `lease_owner`, so a frozen worker that wakes up later cannot move Steps or finish the Run. The lease watchdog (`lost` signal, 90 s) only stops work earlier; correctness rests on the fence. **Ledger writes are the exception** and are not fenced on the token: they describe changes already made on a provider and are always kept (ADR-0342).
- **Lock order: Migration row, then Run row, both `FOR NO KEY UPDATE`.** `createRun` (guard), `requestRunCancel`, `finishRun`, run findings and `settleOrphanedMigrations` lock the Migration first. Step-level writes (Step state, ledger, log) lock only the Run row and never take a Migration lock afterwards. Locking in the opposite order could deadlock with `createRun`, whose insert waits on the partial unique index while a finishing transaction holds the old Run. Both rows are locked `FOR NO KEY UPDATE`, never `FOR UPDATE`: the foreign-key checks of the rows the executor inserts (`mutation`, `expected_difference`, `run_step`, `run_log`) take `FOR KEY SHARE` on the Migration and Run rows, and `FOR UPDATE` conflicts with that. The first version used `FOR UPDATE` and deadlocked a ledger write (holding the Run, needing a share lock on the Migration) with a cancel (holding the Migration, waiting for the Run); the ledger insert was aborted and the target change went unrecorded. `ctx.transaction(fn, { migration: true })` takes the Migration first for a Step that updates it. The staleness trigger and `markAnalysesStale` lock Migration rows `FOR UPDATE` in id order (ADR-0310): they never wait for a Run row, so they cannot close a cycle with the executor, and they were left unchanged. A ledger write that PostgreSQL still aborts (`40P01`, `40001`) is retried up to 5 times with a short random backoff. When the retries run out, the attempt fails with a retryable `transient` error: `apply` is idempotent, so the Step retries within its failure budget (ADR-0341) and records the change again. The record is not lost while the Step is retried, because the change has not been acknowledged yet; a Step that keeps failing ends as a failed Step like any other.
- **Delay and hand-off share `handOffRun`.** A rate limit (`AdapterError` code `rate_limited`, delay from `retryAt`, else `retryAfterMs`, else 60 s, at least 1 s), a Step returning `{ status: 'delay' }` (scratch space, JOB-015) and a SIGTERM all release the lease into a hand-off marker and enqueue `run.execute` under the stable id `run-<id>:handoff-<token>`, now with an optional `delayMs`. `JobContext` carries no job token, so `moveToDelayed` (JOB-044) is not available; a delayed job is the same mechanism with a delay. The reaper sees a pending marker and a delayed job and only extends the wait; the resume counts nothing (ADR-0212). The Step goes back to `pending` with `delays + 1`. Rate limits are unbounded (the quota service decides); a Step bounds its own delays through `ctx.step.delays` (JOB-015: 6).
- **SIGTERM** is checked between Steps only. The current Step is not interrupted and its signal is not aborted (LIF-046: "finishes its current step").
- **Cancel.** (Round 2: `requestRunCancel` locks the Migration, then the Run row, and decides on the locked state; a start that races it either won, so the cancel only sets `cancelRequestedAt`, or lost, so its `UPDATE ... WHERE status = 'queued'` finds a cancelled Run. A Run whose lease holds a **hand-off** marker, such as one waiting for a delayed job, is finished directly instead of waiting for the job. A reaper **resume** marker is not: the old worker may be alive and about to record a change, so the cancel is only requested and the resumed executor finishes the Run, with that change counted (round 3, ADR-0342).) `Run.cancelRequestedAt` (new column). `requestRunCancel` cancels a `queued` Run directly (and returns the Migration to `statusBeforeRun` through `run_finished(cancelled, no mutation)`), and sets the column for a `running` one. The executor polls the column every 2 s (`cancelPollMs`) and before every Step, and aborts `ctx.signal` (merged with the lease watchdog). A Step passes the signal to provider calls and git, and calls `ctx.checkpoint()` in loops. The interrupted Step is stored `failed` with `{ code: 'run.cancelled' }`, the remaining Steps `skipped`, and the Run `cancelled`; the Migration transition is LIF-002's `run_finished(cancelled)`: `partial` if the Run recorded any Mutation, else `statusBeforeRun`.
- **Ending a Run** (`finishRun`) is one transaction under the Migration and Run locks: pending Steps to `skipped`, the Run's status, `finishedAt`, error and cleared lease, the `run_finished` transition (and its effects `set_source_read_only_applied` and `reset_flags`), and the `run.updated` and `migration.updated` events. A crash leaves either a running Run or a finished one with a settled Migration, never both inconsistent. Outcome: any `fatal` Step failed means `failed`; else any `independent` failure means `partial`; else `succeeded`; `advisory` failures are ignored (ADR-0341).
- **An executor crash** (an exception outside Step code, such as a planner bug or the database being down) does not release the lease: `lease.stop()` and a rethrow. The lease expires, the reaper resumes the Run and counts the resumption, so a deterministic crash ends in `run.abandoned` after 3 resumptions (LIF-046) instead of looping. Exceptions inside a Step are Step failures, never crashes.
- **Inline Analysis (LIF-021, LIF-022)** runs once, for `migrate`, `run_anyway` and `resync` Runs that have no `analysisId` yet, through an injected `RunAnalysisPort` (`analyzeForRun` plus the failure marker). Resumes skip it. `Run.analysisId` is set to the Migration's latest Analysis when it passes.
  - Readiness worse (`readinessWorsened`): the Run ends `cancelled` with error `{ code: 'readiness_changed', before, after }`, no Step rows exist, and the Migration returns to `statusBeforeRun`. LIF-022 says "aborts with `readiness_changed`" without a status; `failed` would set the Migration to `failed` ("failed in steps 1 to 5"), which is untrue because nothing ran, and a `cancelled` Run with no Mutation maps to exactly the right lifecycle row.
  - An Analysis that throws (the known gap of ADR-0310): the Run ends `failed` with `{ code: 'run.analysis_failed', ... }` and `recordAnalysisFailure` writes the feeder's failure marker (ADR-0312), exactly as the `analysis.migration` handler does for its jobs. A rate-limited Analysis delays the Run. An Analysis that was skipped (`source-missing`, `route-retired`) fails the Run with `run.analysis_skipped`.
- **Events** (`run.updated`, `migration.updated`, `run.log`) are published with `publishEventIn` in the transaction that changes the state, so a listener never sees a state that was rolled back. `ctx.runLog` appends to `RunLog` (message scrubbed with `stripText`, capped at 2,000 characters) and publishes `run.log`.
- **Stored errors** (`serializeStepError`) keep `code`, `message` (scrubbed, at most 500 characters), `retryable`, `provider` and the request without secrets; never a stack. Messages pass `stripText`, so a URL with credentials is not stored.

## Alternatives

- Compute Steps once at Run creation and store the whole plan: couples creation to the registry and loses the ability to see a renamed Step during a deploy.
- Re-enter the lease on the same worker for a delayed resume: LIF-046 forbids re-entrance.
- `failed` for `readiness_changed`: wrong lifecycle row, see above.
- Abort the Step on SIGTERM: LIF-046 says finish the current Step; interrupting a 20 GB push would waste more than the termination grace period saves.
