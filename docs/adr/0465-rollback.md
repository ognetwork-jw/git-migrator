# ADR-0465: Rollback of a created target, an adopted target and an endpoint Run

- Status: agent-decided
- Date: 2026-10-09
- Task: T-089
- Affects: LIF-077, LIF-045, LIF-031, LIF-002, LIF-005, LIF-070, LIF-080, LIF-081, AUTH-050, FAC-ACL-004, ADP-012, API-020

## Context

LIF-077 says what a rollback does (delete a created target after typed confirmation, otherwise undo the target Mutations in reverse order and leave git refs, with an `undo_source_read_only` Run first) but not how the Steps are built, how "created" is proven when the ledger holds only an unconfirmed create, what "available" means in the guard, or how an endpoint Run is rolled back. Open follow-ups asked T-089 for four things: close the hand-made empty repository hole of T-071 before rollback deletes repositories; return the Group Mappings of undone teams to `unmapped` and stale the Route's Analyses (T-086); keep rollback from running while a source-lock intent is open, or gate it (T-073); and use the Facet drivers to revert an adopted target (T-033, ADR-0467).

## Decision

- **Availability is the guard's (`createRun`).** A `rollback` Run is refused with `run.not_permitted` (409 `run_not_permitted`) when the Migration is `discovered` or `rolled_back` (the lifecycle table already refuses `running` and `source_missing`), when it has no target repository and no undoable Mutation on either side (LIF-077 "provided the Migration has a target or Mutations to undo"; adopted, no-op and `not_applied` records do not count, the SQL twin of `isUndoable`), or while the source is locked. The typed confirmation (T-074, ADR-0415) is still checked, after these. Readiness never gates it (LIF-005).
- **"Undo first" is a refusal, not an embedded step (T-073 follow-up).** A rollback is refused while `sourceReadOnlyApplied` is set **or a write of the source lock is unsettled** (`hasOpenLockIntent`), with a message naming `undo_source_read_only`. The UI offers the two in sequence, as LIF-077 says. A rollback reads and translates no source state (it reverts the target's own ledger), so the gate of migrate and resync (`branch-rules.source-lock-unsettled`) is not needed for translation; the refusal is for a different reason: a source that may still be locked would be left pointing at a target that is gone, and `undo_source_read_only` is the Run that records an unrecorded lock and removes it (ADR-0425). `undoSourceReadOnlyStep` is not reused inside the rollback: one Run, one concern, and the settle logic stays in one place.
- **Three Steps.** `rollback.target` (fatal), `rollback.group-mappings` (independent, endpoint Runs only) and `rollback.settle` (fatal). No Analysis is run for the kind (it is not in `ANALYSIS_GATED_KINDS`).
- **A created target is deleted only on proof.** The proof is the one T-071 uses to adopt (`creationRecorded`, `ledgerShowsCreation` in `migrate/repository.ts`, now exported): a recorded, non-adopted `create` of exactly the Migration's target by provider id; `targetCreatedByFramework` alone is not enough (`rollback.deletion-unproven` fails the Step). The deletion goes through `repositories.delete` with the provider id, which the adapter refuses without and when the name now holds another repository (`conflict`: the repository this Migration created is gone, nothing is deleted). A repository that is already gone is success (idempotent).
- **A create whose response was lost (T-071 follow-up).** An unconfirmed `create` intent of a repository counts as the framework's only when the repository is empty, the provider created it no earlier than the intent was written **and no later than the Run's last recorded activity plus 60 seconds** (`INTENT_SETTLE_MARGIN_SECONDS`; Round 2 replaced the first bound, the Run's end, because a late reaper widened it). A repository somebody made by hand and left empty after the Run ended is therefore adopted by a later migrate and left alone by rollback; the intent is settled `not_applied`. The margin covers a create request that was sent just before a cancel and lands after the Run is finished, and clock skew between the provider and us; a hand-made empty repository created inside that minute is the residual risk, and the other tests (empty, not earlier than the intent) still apply. The same function decides adoption (`ensure`, `adopt`) and rollback, so the two cannot disagree.
- **An adopted target stays.** The framework's writes are reverted newest first (`mutationsToUndo`), one record at a time, and each record is marked `undone_at` as soon as its revert is done (a crash repeats at most one revert, and every revert accepts state that is already gone). Facet records go to the target driver's `undo` (ADR-0467). A framework Change Request (`change-request` create with its `purpose`) is closed through `changeRequests.close`. Git content is left as it is: `git-push`, `lfs-push`, `git-reconcile`, `default-branch` and `ref` records (including the framework's `git-migrator/*` branches, which the adapter has no writer to delete) are marked undone without a call, and a title patch on a Change Request is covered by closing it. If the target repository is gone, the rest is marked undone. A record the framework could not record exactly (`recovered-write`, ADR-0380: a write whose own record was lost in a crash) has no exact reverse and is **not** reverted; it is not marked undone either, so `rollback.settle` fails the Run `rollback.incomplete` and names what is left, and the Migration becomes `partial` rather than claiming `rolled_back`. This is deliberate and reported as a follow-up (an operator cleanup path).
- **A rollback that changed the target counts as having recorded a Mutation (LIF-002).** Its reverts are not ledger rows, so `rollback.target` sets `Run.hasMutations` before its first change (the deletion, a Change Request close or a driver `undo`). A cancel that lands halfway then leaves the Migration `partial` (the table's "cancelled: `partial` if this Run recorded any Mutation") instead of returning it to a status the target no longer has.
- **Settling.** `rollback.settle` runs in one transaction under the Migration row lock (and the Run's): it re-reads the ledger and fails with `rollback.incomplete` if any target record is still undoable, which is what ADR-0342 asked of rollback (a late write of an earlier Run is serialized against this read). When the framework created the repository it then clears `Migration.targetRepositoryId` and sets the target `Repository` row to `missing`; it deletes the Migration's ParityResults (there is no target to compare) and marks its Analysis stale. The lifecycle resets `targetCreatedByFramework` and `sourceReadOnlyApplied` and moves the Migration to `rolled_back`; the next Analysis returns it to `analyzed` (LIF-002). Rollback triggers no Parity Check: `rolled_back` is not a status parity checks (LIF-062), so there is nothing to enqueue. `framework_mutation` Expected Differences are left as they are: revoking them would make a later migration of the same Migration skip re-creating them (ADR-0342, a revoked difference is an operator's decision).
- **A refused deletion fails the Run with guidance.** `forbidden` or `blocked_by_provider` on the delete adds the run-origin post task `repository-settings.deletion-forbidden` (guidance: allow repository deletion for the organization, or delete by hand and roll back again) and fails the Step with that code; the Migration is `partial`, nothing else is reverted, and a second rollback after the policy changes succeeds. It is a post task, so readiness is untouched; the code is declared by the `repository-settings` Facet, has guidance and is listed as agent-decided in the spec cross-check.
- **Endpoint Runs (T-086 follow-up).** The endpoint Migration has no repository: its Run's records (teams, memberships, organization variables and hooks) are reverted through the same driver `undo`, newest first, so memberships go before their team. `rollback.group-mappings` then moves the Route's `confirmed` GroupMappings whose target Group is a team this Migration created and rolled back (and that is no longer live on the target) to `unmapped` with no target Group, conditionally on the status and Group read under the locks (the target Endpoint's invitation lock, then the Route mapping lock, ADR-0370), writes one `group-mapping.unmap` AuditEvent with no Actor each (`origin: run`, `reason: rollback`, as `group-mapping.confirm` does), and marks **every** Analysis of the Route stale (`markAnalysesStale({routeId})`), so `access-control.team-missing` appears again in the repositories' next Analysis. A mapping an operator changed meanwhile, or whose team exists again, is not touched.

## Alternatives

- Run `undo_source_read_only` as the first Step of the rollback: hides a second Run kind's failure modes inside one Run, and LIF-077 says a Run "must succeed first".
- Delete whatever sits under the target name when `targetCreatedByFramework` is set: one wrong flag (or a repository replaced by hand) deletes a customer's repository.
- Revert an adopted target by applying the `before` documents with `apply`: `apply` never deletes target-only items (except branch rules), so a created hook, key or variable would stay (ADR-0467).
- Mark an unrecoverable record undone with a warning: the Migration would claim `rolled_back` while the target still holds the framework's change.

## Affected requirements

LIF-077, LIF-045, LIF-031, LIF-002, LIF-005, LIF-070, LIF-080, LIF-081, AUTH-050, FAC-ACL-004, ADP-012.

## Round 2 (review findings)

- **"Not found" is not "gone".** A missing target counts as gone only when the provider says so positively: the new optional `inventory.findRepositoryById(providerId)` (GitHub: the GraphQL `node` of the repository's node id, then a check that the installation sees all repositories, `GET /installation/repositories`) returns the record wherever it is named now, or `null` only for an installation that sees everything; an installation limited to selected repositories throws `forbidden` because it cannot tell. `rollback.target` looks the target up this way before it marks anything undone or releases it. Anything else (no such lookup in the adapter, `forbidden`, `not_found`) fails the Step `repository-settings.target-unreadable` and adds the run-origin post task of the same code (a new, agent-decided code with guidance, declared by the `repository-settings` Facet; the closed list accepted it, so no existing code was reused). Nothing is marked undone and the Migration keeps its link; after the installation can see the repository, a second rollback succeeds.
- **`conflict` on delete is not "gone" either.** On `conflict` (the name holds another repository) or `not_found` the repository is looked up by id: renamed, it is deleted under its current name (the adapter checks the id again, once); positively gone, it is gone; otherwise the Step fails `target-unreadable`. A repository somebody made on the old name stays.
- **The open-create-intent path never takes another Migration's repository.** A repository that another Migration has as its target, or whose creation (or adoption) another Migration recorded (`repositoryHeldElsewhere`), is skipped and the intent is settled `not_applied`. The time window is bounded by the Run's last recorded activity, not by `finished_at` alone: the upper bound is `LEAST(finished_at, GREATEST(intent time, latest Step update that was not skipped))` plus the 60 s margin, so a reaper that ends an abandoned Run an hour late does not widen it (the Run has no heartbeat column; Step updates are the recorded activity).
- **A recorded repository create on a Migration whose target is now another repository** (adopted) no longer fails every rollback: it is undone once the by-id lookup says it is gone, and left, reported through `rollback.left-in-place`, when it still exists.
- **Records a driver leaves.** `FacetDriver.undo` may return `{left: reason}` (ADR-0467): the record stays recorded and undoable, the other records are still reverted, and the Step then fails `rollback.left-in-place` naming each reason, so the Migration ends `partial`. A `recovered-write` stays unreverted and fails `rollback.incomplete` at settle; this is pinned by an integration test and remains a follow-up.
- **An endpoint rollback is refused while it would delete a team a live repository Migration depends on.** `createRun` looks for an active, target-side `access-control` write of a repository Migration of the Route (status neither `rolled_back` nor `discovered`) whose principal is `group:<id>` of a team this endpoint Migration created and has not undone, and refuses with `run.not_permitted`, saying so in `detail`. The team record carries the provider id for this (ADR-0467).

## Round 3 (review findings)

- **A renamed target is deleted under its current name.** The old name of a renamed repository answers a read with a redirect and a write with a 307, which the HTTP client rightly refuses to follow. `repositories.delete` therefore sends the DELETE to the `full_name` of the verified read, never to the stored slug. The fake GitHub redirects a renamed repository's old name (301 for GET and HEAD, 307 otherwise) until a repository is made on it.
- **`findRepositoryById`.** An empty id is `invalid`. Once the GraphQL `node` lookup names a repository it never answers "gone": a read by that name that disagrees (a rename or delete in between) is retried once, then it is a `conflict`, which the rollback reports as `target-unreadable`. A repository transferred to another owner counts as gone (the reason given here, that it is no longer visible, is superseded by Round 4: a public one stays visible, so the owner is checked).
- **A gone adopted target.** Before the framework's records are marked undone in bulk, every `repository` create record of another repository is checked by id; one that still exists is left and reported.
- **Teams in use, again.** `rollback.target` re-checks, before each team delete, whether a live repository Migration of the Route holds a grant for that team (the admission guard can be overtaken); if so the team is left. Branch-rule push restrictions and CODEOWNERS references to a team are not counted.
- **Guidance for what a rollback leaves or refuses.** `repository-settings.left-in-place` (one post task with a step per kind: teams, access grants, repositories of earlier Runs) and `repository-settings.deletion-unproven` are raised before the Run fails with `rollback.left-in-place` and `rollback.deletion-unproven`. `rollback.incomplete` (raised in the settle transaction, after `left-in-place` already told the operator) has no task of its own. The steps per kind are amended by Round 4.

## Round 4 (review findings)

- **A transferred repository is gone from the organization, and is checked as such.** A public repository transferred to another owner is still readable by the installation, by its node id and by name. `findRepositoryById` therefore compares the owner in the GraphQL `nameWithOwner`, and then the `owner.login` of the REST read, with the organization (case-insensitively): another owner means `null`, gone. Before, a transfer followed by a new repository on the old name made the adopted undo write to that unrelated repository. `repositories.delete` refuses with `conflict` when the `full_name` of its verified read has another owner than the reference; the rollback then looks the repository up by id, finds it gone, deletes nothing and releases it.
- **A redirected write never ends in a bare `invalid`.** When the repository is renamed or transferred after the rollback's lookup, its old name answers a write with a 307, which the HTTP client does not follow (`invalid` with a 3xx status). `rollback.target` catches that around every write to an adopted target and looks the repository up by id again: gone, the remaining records are settled as for a gone target; still in the organization, the Step fails `repository-settings.target-unreadable`. Nothing more is written either way.
- **Memberships of a team in use stay too.** The in-Step `teamsInUse` re-check applies to `team-membership` records (by their `teamId`) as well as to the team record, so the members of a team that a repository Migration still grants access to are not removed before the team is left.
- **One open `left-in-place` task per Migration, with the current list.** Its `details` are structured `{kind, name}` entries (ADR-0467 round 4). When a rollback raises it again, the open run-origin `left-in-place` tasks of the Migration with another list are dismissed by no Actor, with the note `superseded by a later rollback`, and the task with the current list is reopened if that rule dismissed it before; a rollback whose target Step leaves nothing dismisses them all. The guidance no longer offers "confirm that it should stay and mark this task done", which settled nothing: a repository of an earlier Run is deleted by hand (then the operator rolls back again), or an administrator is asked. The step for access grants is gone (an identity grant is no longer left, Round 3 of ADR-0467) and a step for branch rules replaces it.
- **Accepting what a rollback left has no operator path.** A repository an earlier Run created that must stay, or a branch rule that was replaced or made again, keeps every later rollback from completing: nothing tells the framework to stop reverting it. This is a follow-up, like the cleanup path for a `recovered-write`.

## Round 5 (review findings)

- **Owners are compared by stable id.** `findRepositoryById`, `getRepository` (when the name leads to another login) and `repositories.delete` compare the repository's `owner.id` with the organization's provider id (the reference's namespace id, else `GET /orgs/{org}` once), never the login. A renamed organization keeps its id, so its repositories are still found and a created target is still deleted; a transferred repository has another owner id and is gone. If the organization was renamed and the connection cannot read it under its old name, a lookup fails and the rollback reports `target-unreadable`, never "gone".
- **The target is read before every write.** Before each driver `undo` or Change Request close on an adopted target, `rollback.target` reads the repository under the name it writes to; another provider id, or nothing there, takes the re-lookup path (gone: the rest settles as for a gone target; still in the organization: `target-unreadable`). A write that is answered `not_found`, like one answered with a redirect, takes the same path. This narrows the race of Round 4 (a transfer and a new repository on the old name between the lookup and the writes) to the moment between that read and the one write after it; it cannot be closed, because the provider has no conditional write by repository id.
