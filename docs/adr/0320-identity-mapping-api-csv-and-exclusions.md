# ADR-0320: Identity and Group mapping endpoints, CSV rules, exclusions, staleness and events

- Status: accepted (spec updated)
- Date: 2026-10-08
- Task: T-084
- Affects: AUTH-050, AUTH-021, AUTH-022, API-020, API-011, UI-027, UI-028, JOB-060, LIF-063

## Context

API-020 lists the mapping write endpoints but not how the UI reads them, and AUTH-050 leaves several points open: what a CSV `invite` does, what the exclusion Expected Differences are keyed on, how they are tied back to the mapping that created them (so that reselecting or unmapping can revoke them), how staleness is marked, and which event a mapping change publishes. ADR-0270 has no mapping topic.

## Decision

1. **Reads.** Four read endpoints serve the pages, all with the `read` capability: `GET /routes`, `GET /routes/{id}/identity-mappings` (cursor pagination, `status` and `q` filters, source and target Identity joined, exclusion reason), `GET /routes/{id}/group-mappings` (member counts, collision flag) and `GET /routes/{id}/target-identities` (search for "change target"). RPC would need several round trips and could not compute collisions. Writes use the spec's `POST` paths with `decideMappings`. The three Identity decisions share `{confirm|exclude|unmap}` and the two Group decisions `{confirm|rename}`; the body is optional.
2. **Confirm.** Confirms the suggested target, or the `targetIdentityId` given. The target must belong to the Route's target endpoint (422) and must not be confirmed for another source (409). Confirming the existing suggestion keeps its `method` and `confidence`; a chosen target is `manual` with no confidence. `exclude` requires a reason of 1 to 500 characters. `unmap` returns the mapping to `unmapped` with no decision, so the matching cascade may suggest again; for a `pending_invite` mapping it is a 409, because the invitation correlation of AUTH-060 step 5 depends on that status and revoking an invitation belongs to the invitation flow (T-085). A decision that changes nothing (same target, unmap of an unmapped mapping, same exclusion reason, same slug) returns the current view and writes no audit event, marks nothing and publishes nothing. A Group Mapping `confirm` needs a target team (the suggestion or one given). `rename` accepts a lowercase slug (`[a-z0-9]` and single hyphens, at most 100 characters) and is refused for a confirmed mapping (409); a slug held by an existing target team makes the mapping `suggested`, otherwise the team is planned for creation (`unmapped`).
3. **Exclusion Expected Differences** are the eight patterns of AUTH-050 step 4 (facets `access-control`, `members`, `teams`, `branch-rules` x4, `code-ownership`), built with `formatFieldPath` (so a `*` in an id is escaped) and validated by `parsePathPattern`. They are created with `reason: identity_excluded`, `migrationId: null` and the acting Actor. The principal id is the source Identity's Provider id; when the mapping had a target, the target's Provider id is covered too, because a diff names a principal the way its document does (translated documents carry target ids). The reason is the `note`, for people only; the link is a nullable `identity_mapping_id` column on `expected_difference` (migration `20261008000010`, indexed, foreign key `ON DELETE RESTRICT` because DOM-004 allows no other deletion behavior here, no write through RPC). Unmapping, confirming, or excluding again revokes (`revokedAt`) the Expected Differences linked to that mapping. Invitation batches (T-085) can use the same column.
4. **CSV.** Header `source,target,action` (case-insensitive, BOM allowed), at most 5,000 data rows, cells at most 320 characters, no control characters, RFC 4180 quoting. `source` matches a Provider account id first, otherwise a login (case-insensitive); `target` for `map` matches a target login, or an email when it contains `@`. Several matches are `*_ambiguous`, none is `*_not_found`. The same source twice, or a target that would be confirmed for two sources, is an error on the later row. `map` confirms (`method: csv`). `exclude` takes no target and records the reason "Excluded by CSV import" (the file has no reason column). `invite` on a mapping that is `confirmed` or `excluded` is the row error `already_decided` (AUTH-050 step 2: decisions are never overwritten; unmap first). Otherwise it takes an email, records it on the source Identity (`emailSource: csv`) when the Identity has none or a CSV one, and leaves the mapping `unmapped` (or `pending_invite` if already so) with `method: csv`; a different provider email is `email_conflict`. Nothing is invited by an import: AUTH-061 holds. Rows whose result equals the present state are `unchanged` and write nothing.
5. **Dry run and apply.** `?dryRun=true` returns 200 with a report per row (`ok`, `errors`, `outcome`) and writes nothing. Apply re-validates in full inside one transaction under a per-Route advisory lock and, if any row or the file is invalid, answers 422 `validation_failed` with the row errors in `errors` and changes nothing. The body must be `text/csv` or `text/plain` (415 otherwise).
6. **CSV injection.** A `target` starting with `=`, `+`, `-`, `@`, tab or carriage return is rejected (`formula_prefix`); no valid login or email starts that way. Cells echoed in a report are prefixed with an apostrophe when they start with one of those characters (`neutralizeCell`), so a report copied or exported to a spreadsheet stays text. The UI displays the neutralized cell.
7. **Staleness.** Every write that changes a mapping (confirm, exclude, unmap, CSV apply when any row changed, Group confirm and rename) calls `markRouteAnalysesStale` in the same transaction, which calls the shared `markAnalysesStale(tx, { routeId })` of `packages/db` (ADR-0310): the generation of every Migration of the Route is bumped, also those never analyzed or already stale, on the database clock, with row locks in id order and failure markers lifted. No-op decisions mark nothing. The mapping writes touch no Migration row themselves and no staleness trigger sits on the mapping tables, so the only Migration locks come from that helper and cannot deadlock with a trigger.
8. **Events.** ADR-0270 has no mapping topic, so no event type is added. When the helper newly marks any Migration stale, one `migration.updated` event without ids is published in the same transaction (the helper publishes nothing itself) (delivered on commit); it reaches `list:migrations` only, so Migration lists refresh whatever the number of Migrations. The mapping pages refetch after their own mutations and on window focus.
9. **Audit.** Every decision writes an `AuditEvent` (`identity-mapping.confirm|exclude|unmap|import.<action>`, `group-mapping.confirm|rename`) with status transitions and, for exclusions, the reason; no emails are logged.

10. **Apply cost and limits.** Apply loads Identities and mappings once. Every bulk write is chunked so a statement stays far below PostgreSQL's 65,535 bind parameters (2,000 rows per `createMany` or `createManyAndReturn`, since an exclusion writes 8 Expected Differences per principal and a 5,000-row import writes 40,000). Updates of existing mappings and the email updates of invitations are one `UPDATE ... FROM unnest(...)` per 5,000 rows, with every value a bind parameter. It holds the per-Route lock with `lock_timeout` 15 s and `statement_timeout` 60 s (the ORM has no transaction timeout option); a request that times out on either (SQLSTATE 55P03, 57014) answers 503 `busy` with `Retry-After: 5`. The 5,000-row cap stays; tests apply 5,000 new and 5,000 existing mappings.
11. **Echo.** A report row echoes `action` only when it is one of `map`, `invite`, `exclude`, and `invalid` otherwise. A source that matches one Identity by account id and a different one by login is `source_ambiguous`.

## Alternatives

- Reading through the RPC mount: rejected, see 1.
- A new `mapping.updated` event and `list:mappings` topic: rejected, it widens ADR-0270 and JOB-060 for little gain.
- Partial CSV apply that skips bad rows: rejected, AUTH-050 says the import is validated in full before anything is applied.
- Setting `pending_invite` on CSV `invite`: rejected, AUTH-060 step 4 makes the sending job set it, and acceptance correlation depends on that.
- Keying exclusion Expected Differences on the target id only: rejected, an excluded user may have no target.

## Addendum (review round 3)

- **CSV `map` and `exclude` may replace an earlier decision.** They are explicit operator decisions and are audited; AUTH-050 step 2 protects decisions from the matching cascade, not from the operator. The dry run reports such a row with the outcome `replaces_decision` (and counts it in `summary.replaced`) so the operator sees it before applying. Only `invite` is refused on a decided mapping (`already_decided`), because an invitation is not a decision.
- **Failure markers.** `markAnalysesStale` also lifts failure markers. A mapping change that only lifts markers or bumps the generation of Migrations that were stale already publishes no event, because no list shows a difference.
- **Foreign key.** `expected_difference.identity_mapping_id` is `ON DELETE RESTRICT`. No flow deletes `identity_mapping` rows (no retention or pruning job touches them; `unmap` resets the row), so the restriction never fires.
