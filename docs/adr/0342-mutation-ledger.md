# ADR-0342: Mutation ledger writes and Expected Difference derivation

- Status: agent-decided
- Date: 2026-10-09
- Task: T-070
- Affects: LIF-045, LIF-063, LIF-002, ADP-011, ADP-012

## Context

LIF-045 says every write records a Mutation and that target-side Mutations "on resources that are not part of the desired document" create `framework_mutation` Expected Differences, but not how the executor knows whether a record is part of the desired document, in what order undo reverts, how a record with no Facet is keyed, what an adapter that sends an adopted record with unequal images gets, or what counts as "recorded any Mutation" for the cancelled row of LIF-002.

## Decision

- **Writer.** Steps call `ctx.ledger.record(write, records)` (one transaction, before returning) or `ctx.ledger.recordAll(write, asyncIterable)`, which persists each record when `apply` yields it. When `apply` throws after some changes, the earlier records are already stored (ADP-011, ADR-0222), and the Step's retry adds only what is new because `apply` is idempotent. A ledger write is **not** fenced on the lease token (round 2): it locks the Run row and requires only that the Run exists. A record describes something that already happened on a provider, so dropping it because the lease expired in the meantime would leave a real target change that rollback cannot find; a duplicate record is harmless because undo is idempotent. The Step's own state writes stay fenced, so a worker that lost the lease stops, but what it already did is recorded.
- **Late writes (rounds 3 and 4).** A write that lands after its Run finished is still recorded. The ledger transaction reads the Run's status first; for a finished Run it locks the Migration, then the Run (lock order), counts the records before and after, and reconciles when records were added (`late.ts`; confirming an intent adds none). **One rule:** (a) the narrow case, a `cancelled` Run whose first Mutation this is, with no later Run and the Migration still at the status the cancel gave it (`status = statusBeforeRun`): the Migration takes `run_finished(cancelled, recordedMutation = true)` again through `transition()`, which checks LIF-003 legality, and becomes `partial` (LIF-002); (b) every other case, whatever the Run's status (`failed`, `succeeded`, `partial`, `cancelled` with an earlier Mutation), later Runs, or the Migration's status (including `rolled_back`): the Migration is not rewritten; a run-origin blocker `run.late-mutation` (`{runId, mutationId}`, LIF-049) is added, the Analysis is marked stale (`markAnalysesStale`), `migration.updated` is published and a warning is logged, so an operator looks before anything else is done to a target holding a change nobody expected. The direct cancel of a Run whose lease holds a reaper `resume` marker is gone (ADR-0340), which closes the usual way to get here. **For T-073:** rollback must take the Run row lock (`lockRun`), which serializes it against late writes, and re-read the ledger when it ends.
- **Intents.** `ctx.ledger.intend(write, record)` stores the record with `state = 'intended'` before a provider call whose outcome could be lost (a timeout or a crash), and `ctx.ledger.confirm(id, 'applied' | 'not_applied', actual?)` settles it (`recorded` or `not_applied`). `mutationsToUndo` includes an unconfirmed intent and `isPossiblyApplied` says so: undo must tolerate that the change is not there. `not_applied` is skipped. `confirm` settles only an `intended` row of the same Run (a second confirm throws); `not_applied` revokes the Expected Differences only that intent caused (`mutation.derived_differences` remembers which, and one still needed by another live record stays); `applied` with `actual` derives the Expected Differences of what really happened. `mutation.written_by_step` and `ctx.ledger.openIntents()` let a resumed Step find the intents it left open and reconcile them (read the provider, then `confirm`). T-071 should `intend` before every create it cannot read back (repository, rule, hook, key, grant) and `confirm` after the response or a read-back.
- **`LedgerWrite`** carries `side`, `origin` and optional `differences`. `origin: 'desired'` is a Facet `apply` (the written resource is in the desired document, so parity compares it). `origin: 'framework'` is a resource the desired document does not contain: `git-migrator/*` branches, framework Change Requests, the source read-only restriction. The caller knows this; the adapter cannot. `differences` names the Expected Difference paths for a record with `facetKey: null` (repository-level operations such as a Change Request).
- **Derivation** is the pure function `deriveFrameworkMutationDifferences` in `@git-migrator/core`: a `framework_mutation` Expected Difference per `(facetKey, path)` for target-side, `framework`-origin records that are not adopted or no-op and not deletions. A deletion leaves nothing extra for parity to ignore (the lifted protection rules of step 3a are re-created in step 10 by the desired document). Source-side records derive nothing: source-side Mutations are removed from the source document before translation instead (LIF-045, ADR-0310). The row is `INSERT ... ON CONFLICT DO NOTHING` against a new partial unique index on `(migration_id, facet_key, path)` for active `framework_mutation` records, so a resumed Step records nothing twice. It is Migration-scoped with the Route id.
- **Inert records.** A record with `resourceRef.adopted` or `resourceRef.noop` is stored with `after` replaced by `before` if the adapter sent them unequal (`normalizeLedgerRecord`). `isUndoable` and `mutationsToUndo` (core) are the single definition of what undo reverts: not undone, not adopted, not no-op, newest first. Rollback tasks (T-073 and later) must use them.
- **Columns this task adds to `mutation`:** `seq` (recording order, unique), `state` (`intended`, `recorded`, `not_applied`), `written_by_step` (the Step row that wrote it), `origin` (`desired` or `framework`) and `derived_differences` (the Expected Differences the record caused). There is also a partial unique index on active `framework_mutation` Expected Differences `(migration_id, facet_key, path)`.
- **`has_mutations` and settled intents.** Settling an intent `not_applied` recomputes `Run.hasMutations` from the records that are not `not_applied`, so a Run whose only records never happened ends as a Run without a Mutation (LIF-002).
- **Revoked differences.** The Expected Difference insert is skipped when any `framework_mutation` record for the same Migration, Facet and path exists, active or revoked, so a resumed Step does not undo an operator's revocation.
- **Order.** `Mutation.seq` (new `BIGSERIAL`, unique) is the recording order. `created_at` has millisecond resolution and `id` is a time-ordered UUID with random tail, so neither orders records written in the same millisecond. `mutationsToUndo` sorts by `seq` itself. `seq` is a `bigint`: the API (T-074) must serialize it as a decimal string, since JSON numbers lose precision above 2^53.
- **`facet_key`** is NOT NULL, so a record with `facetKey: null` is stored under `'framework'`, the same label the plan uses for items without a Facet (`planFacetKey`).
- **`Run.hasMutations`** is set by any ledger row, including adopted and no-op records, following LIF-002 literally ("partial if this Run recorded any Mutation"). An adopted target after a cancel therefore leaves the Migration `partial`, which the next Analysis corrects; the other way (ignoring inert records) risks reporting `analyzed` for a Migration whose target the framework had already taken ownership of.

## Alternatives

- Derive the Expected Difference from the record alone (guess `framework` from the path): a `git-migrator/*` branch is a git-refs path, but other framework resources have no common path shape.
- Let the adapter set `origin`: the contract (ADP-012) is a provider-neutral record; the framework decides what it asked for.
