# ADR-0310: Analysis processor

- Status: agent-decided
- Date: 2026-10-08
- Task: T-061
- Affects: LIF-020, LIF-021, LIF-022, LIF-002, LIF-004, LIF-045, FAC-006, FAC-005, API-012, JOB-020, JOB-060, ADP-011, ADP-014, DOM-003

## Context

LIF-020 lists what an Analysis does but not how its pieces meet: which client writes what, how a Run that starts during an Analysis is kept safe, how read-time capabilities reach `translate`, where staleness is marked for NamingRule, WebhookAllowlistEntry and Overlay writes (API-012 asks for a ZenStack after-mutation hook, which cannot touch `Migration` because every field is `@deny('update')` for the policy client), where `avgCallsPerAnalysis` lives (JOB-020 says "stored per Route" but `Route` has no column), and how LIF-022 is shared with the Run executor.

## Decision

- **Shape.** `packages/jobs/src/analysis/analysis.ts` exports `runAnalysis(deps, migrationId, { shutdown, pool })` and `analysisHandlers`. The handler picks `interactive` or `background` from the queue the job came from (JOB-020), so the quota pool follows the queue. It uses the privileged client (DOM-005), the injected `EndpointConnector` (ARC-012) and only adapter drivers, so every provider call goes through `ProviderHttpClient` and the quota service. `ctx.shutdown.aborted` is checked before every provider read; an interrupted Analysis stores nothing and the job is retried.
- **Scopes.** A repository Migration reads the repository-scope Facets (`git-refs` through `extras`) of the source and, when the target repository exists, of the target. An endpoint Migration (LIF-080) reads the endpoint-scope Facets (`members`, `teams`, `org-*`) of the root Namespace of each Endpoint (the Route's target Namespace on the target side) and uses `ENDPOINT_STEP_TEMPLATE`. Facets with no driver, or whose adapter declares `read: false`, are skipped (`translateAll` reports them as skipped).
- **Rate limits and errors.** A driver error aborts the Analysis and the job fails; BullMQ retries it with the JOB-013 backoff, and `rate_limited` is not retried in-process (ADP-060). The handler does not call `moveToDelayed`: `JobContext` carries no job token, and the feeder only enqueues what the background pool can pay for. A translate-contract violation (`FacetEngineError`) also fails the job. Follow-up: the feeder re-enqueues a Migration whose Analysis keeps failing every minute; a failure backoff needs a place to record it.
- **Capabilities.** Static `ProviderCapabilities` are overlaid with `FacetRead.capabilities` and with `FacetRead.unreadable` (as `unreadable` entries) through `effectiveFieldSupport` (monotone, ADR-0231 section 3), once per side. The target side has read-time facts only when the target repository exists; otherwise its static capabilities apply.
- **Principal resolution (FAC-006).** Identities: `confirmed` with a target maps; `excluded` is excluded; `pending_invite` is pending; everything else (`suggested`, `unmapped`, no row) is `unmapped`. Groups: `confirmed` with a target team maps to the team's provider id; `excluded` is excluded; `suggested` (a team of that slug exists but nobody confirmed it) is `unmapped` so the pre task asks an operator; `unmapped` or no row is `team_missing` (blocker until the endpoint Migration creates the team, AUTH-050 last paragraph). Group ids are looked up case-insensitively. Mappings are loaded only for principals that appear in the documents read (FAC-006: unrelated membership never matters), except for the endpoint scope, which needs every group mapping by slug.
- **LIF-045 filtering.** Before translation, the elements addressed by the `paths` of active (not undone) source-side `create` Mutations of the Migration are removed from the source documents (`withoutFrameworkCreated`); a Mutation marked `resourceRef.adopted` or `noop` removes nothing. The stored Snapshot is the read as it was. Paths address the same elements as `resourceRef`, and need no adapter knowledge.
- **Persistence (LIF-020 steps 6 and 7)** is one transaction: Snapshots, Analysis, PlanItems, ManualTasks, Expected Differences, the Migration update, events. ManualTasks upsert by `(code, facetKey, paramsHash)`. `done` stays `done`. An open analysis-origin task that is no longer produced becomes `dismissed` with note `obsolete` and `completedById` null, whatever the task was before, so the reopen rule always holds; any endpoint that reopens or dismisses a task must keep this invariant (only the Analysis dismisses without an Actor); the same finding coming back reopens it when the task is `dismissed`, analysis-origin and has no `completedById` (T-012 follow-up). The decision does not read `note`, which RPC can edit: an operator who edited the note must not block the reopen and so bypass the LIF-005 gate. `completedById` is denied for update through RPC, so only the Analysis dismisses without an Actor; **every API path that dismisses a task (the `/tasks/{id}/dismiss` endpoint of API-020, bulk actions) MUST set `completedById`**, or its dismissals would be reopened. No `dismissReason` column was needed. A run-origin task with the same identity is never touched. Plan items without a Facet (naming, target) use the code prefix (`naming`, `target`) as `facetKey`. Expected Differences: `lossy_accepted` once per Route, facet, path and policy key; `unreadable_defaulted` once per Migration (ADR-0081). Overlays are not merged into the stored `desired` (LIF-048 applies them in the Run step); an enabled Overlay only adds the `overlays.apply` step.
- **Serialization and the guarded write (LIF-002).** The persist transaction starts with `SELECT ... FOR UPDATE` on the Migration row. Another Analysis of the same Migration, a Run starting, and a staleness trigger in a still-open transaction all wait for it (or are waited for), so what is read next is what is committed. `Analysis.startedAt` is the **database** clock at the start of the Analysis (`clock_timestamp()`); inside the lock, if the stored latest Analysis started later than this one, this one is dropped (`superseded`; nothing is stored, the newer result stays), so a slow older run never overwrites a newer one. Concurrent Analyses therefore cannot collide on a ManualTask (P2002). The Migration is then updated with `updateMany` whose `where` repeats `status` and the four saved statuses, retried if it still moves (a safety net behind the lock). `analysis_completed` is applied with `transition`, so a `running` Migration keeps running and gets the new readiness, and `plannedTargetName` is left alone while it runs.
- **Stale marks during an Analysis: a generation counter.** `Migration.staleGeneration` (bigint, migration `20261008000005_analysis_robustness`) is incremented by **every** marker, unconditionally, for every Migration it affects, including ones that are already stale or were never analyzed: the statement-level triggers, `markAnalysesStale` (which also uses the database clock for `analysisStaleAt`, never a worker's), `syncConfig` (through the helper) and the deploy-key cross-marking. The Analysis reads the generation in the same read as its inputs, before them. Inside the row lock, a different value means something changed after the inputs were read, and `analysisStaleAt` is set to the database `clock_timestamp()` (stale now); otherwise it is `now + analysisStaleAfter` from `deps.now`. A first version compared the stored `analysisStaleAt` with the value read at the start. That is insufficient: the markers only wrote a Migration that had an Analysis and was not stale yet, so a second edit during the Analysis of an already-stale Migration, or any edit to a never-analyzed one, changed nothing and the result looked fresh for seven days. A marker in a transaction that is still open when the Analysis is stored holds the row lock, so the Analysis waits for it and then sees the new generation.
- **Cross-marking** (FAC-DKY-003 holders) runs after the commit, one Migration per statement in id order (each statement locks its rows in id order), and publishes `migration.updated` per newly marked Migration. It holds no lock while another is taken, so two Analyses that mark each other cannot deadlock. Doing it inside the transaction was considered: a plain update in id order can deadlock against the other Analysis' own-row lock, and `SKIP LOCKED` would skip exactly the holder that is being stored right now and therefore needs the mark. An error while marking is logged and does not fail (and so repeat) the stored Analysis; a crash or error in that window leaves the holder fresh until its expiry, which is the accepted cost.
- **Readiness (LIF-004)** is recomputed with `deriveReadiness` from the Plan, every ManualTask of the Migration and `Migration.runBlockers`. `Analysis.readiness` stores the Plan-only value.
- **Staleness is `analysisStaleAt <= now`** (the instant an Analysis becomes stale, LIF-020 step 7). `markAnalysesStale` (packages/db) writes `now` only where the value is null or still in the future; it replaces T-060's helper, which only matched `null` and so never marked an Analysis that had just been given `now + 7 d`. API-012's "after-mutation hook" is a database trigger on `naming_rule`, `webhook_allowlist_entry` and `overlay` (migrations `20261008000004_analysis_staleness`, replaced by statement-level triggers in `20261008000005_analysis_robustness`: one update per statement for the distinct Routes, using transition tables, and one `migration.updated` NOTIFY with empty ids, which topics deliver on `list:migrations`; the per-Route topic of ADR-0270 has no id key, so the list topic is the finest the event shape allows): the ZenStack hook runs as the Actor, whose policies forbid writing `Migration`, and a trigger also covers writers that bypass the policy client. Any such write marks every Migration of the Route (naming collisions are cross-repository). Route configuration changes are marked by `syncConfig`; identity and group mapping changes by inventory (AUTH-050 step 5; a mapping change counts when it changes what the resolver returns: for identities `confirmed` is the only resolving status, for groups `suggested` resolves to `unmapped` while `unmapped` and no row both resolve to `team_missing`, so a team appearing or disappearing marks the Route and a mapping created as `unmapped` does not). **Any future endpoint that edits an Identity or Group Mapping (confirm, exclude, CSV import, endpoint Migration creating a team) MUST call `markAnalysesStale` for the Route** (AUTH-050 step 5); nothing in the database does it for them. Marking also clears the failure markers of ADR-0312.
- **`avgCallsPerAnalysis`** is a `Route` column (default 30) updated after each Analysis with an exponential moving mean, weight 0.1, from the number of requests the drivers made through the HTTP client (counted by a proxy around `connection.http`) plus the target lookups. This is "a rolling mean stored per Route".
- **Expected Differences** the Analysis records are inserted with `INSERT ... ON CONFLICT DO NOTHING` against a partial unique index over the active `lossy_accepted` and `unreadable_defaulted` records, so concurrent Analyses cannot repeat one.
- **Events (JOB-060).** In the same transaction, `migration.updated` for the Migration, and `task.updated` for up to 25 created, reopened or dismissed tasks.
- **LIF-022.** `analyzeForRun(deps, migrationId, ...)` re-analyzes inline on the interactive pool when `needsReanalysis` (no Analysis, stale, or older than `schedules.runRequiresAnalysisWithin`) and returns `{ reanalyzed, before, after, worsened }`; `worsened` means `readinessWorsened(before, after)` and tells the Run executor (T-070) to abort with `readiness_changed`.
- **Git.** The `git-refs` driver needs `GitClient.lsRemote`. The worker passes `createAnalysisGitClient` (a `GitService` without quota pre-acquire). One unit per Analysis in a bucket of 60,000 per hour is not charged because the host cannot name an adapter's git bucket; follow-up with the credential-selection hook of ADR-0281.

## Alternatives

- A ZenStack hook for staleness: cannot write `Migration` under the Actor's policies; a second, privileged client would not join the mutation's transaction.
- Store the call mean in `Route.defaults`: that column is rewritten from configuration.
- Pass a job token so the handler can `moveToDelayed`: needs a runtime change outside this task.

## Affected requirements

LIF-002, LIF-004, LIF-020, LIF-021, LIF-022, LIF-045, FAC-005, FAC-006, API-012, JOB-020, JOB-060, ADP-011, ADP-014.

## Lock order (round 4)

Every writer that updates several Migration rows takes the row locks in **id order**: the staleness trigger function (`mark_routes_stale` runs `SELECT ... ORDER BY id FOR UPDATE` before its UPDATE, TRUNCATE included, because an UPDATE alone locks in plan order), `markAnalysesStale` (a CTE `ORDER BY id FOR UPDATE`), and `syncConfig`, which collects all changed Routes and marks them with one call so a single statement locks them all. The Analysis's persist transaction locks only its own row and updates only that row; cross-marking is one row per statement after the commit. With one global order and no transaction that holds one Migration lock while waiting for another out of order, the writers cannot deadlock; `staleness.test.ts` holds a row lock and queues the trigger and the marker behind it.
