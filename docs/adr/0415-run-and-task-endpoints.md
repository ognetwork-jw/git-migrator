# ADR-0415: Run, task and Expected Difference endpoints

- Status: agent-decided
- Date: 2026-10-09
- Task: T-074
- Affects: API-020, API-021, LIF-005, LIF-006, LIF-020, LIF-021, LIF-040, LIF-043, LIF-062, LIF-075, DOM-010, UI-021, AUTH-022

## Context

API-020 lists `POST /migrations/{id}/runs` (409 if a Run is active, 422 if readiness disallows it), `POST /runs/{id}/cancel`, `POST|DELETE /migrations/{id}/complete`, the task actions and the Expected Difference endpoints, but not the problem codes, the states a task action may leave, what LIF-006's completion modes do at the API, which Expected Differences may be revoked, or what happens when the queue is down after the Run row exists.

## Decision

- **One creation path.** `startRun` (`packages/api/src/run-start.ts`) is the single-item path: `createRun` (the guard of T-070: concurrency, readiness, options, lifecycle, all under the Migration lock) and then `JobRuntime.enqueueRun`. If the enqueue fails, the Run is cancelled with `requestRunCancel` (a `queued` Run ends `cancelled` and the Migration returns to its saved status) and the caller gets 503 `not_ready`; a Run never waits `queued` without a job. T-088's `bulkMigrate` follows the same sequence. Readiness for a Run kind stays in `allowedReadiness` (LIF-005) inside `createRun`; the endpoint has no second check. A later force-adopt waiver changes that one function.
- **Problem codes.** Three codes are added to `PROBLEMS`, so the UI can tell the cases apart: `run_active` (409, DOM-010), `readiness_required` (422, LIF-005) and `confirmation_required` (422, LIF-043). Other guard refusals use the existing codes: `conflict` for `run.not_permitted` (the lifecycle table does not list `run_started`, for example a `source_missing` Migration) and `run.route_retired`, `validation_failed` (with `errors[].path = options`) for invalid options, `not_found` for an unknown Migration. `apps/web/messages/en.json` has a text for each (a test pins one per code).
- **Cancel.** `requestRunCancel` decides: `cancelled` or `requested` answer 200 with the outcome; a finished Run is 409 `conflict`; an unknown Run is 404.
- **Capabilities.** Runs and cancel: `operate`. Complete and revoke: `markComplete`. Tasks and Expected Differences: `manageTasks`. All three are operator (AUTH-020).
- **Manual completion (LIF-075).** `mark_complete` and `revoke_complete` go through `transition()`, in one transaction under the Migration lock, with `manualCompletion = {actorId, reason, at}` and an AuditEvent. A refused transition is 409 (running, source missing, already completed, not completed). The reason is trimmed and must be 1 to 500 characters. Revoking asks `parityVerdict` whether parity is all equal with no open task, and passes the status of the latest finished Run that changed the status (a cancelled Run counts only if it recorded a Mutation) as `lastRunStatus`; with no such Run it is `migrated`.
- **Task actions (LIF-006).** A task may leave: `open` or `dismissed` by `done`; `open` by `dismiss`; `done` or `dismissed` by `reopen`. Any other pair is 409. `done` and `dismiss` set `completedById` and `completedAt` (LIF-020 step 6: an Analysis would reopen a dismissal that has no `completedById`); `reopen` clears both. By completion mode: `resolution` cannot be `done` (422) and its `dismiss` needs a non-blank `note`; `accept` creates, on `done`, one Migration-scoped `lossy_accepted` Expected Difference per path of the task (`note` = the policy key; `ON CONFLICT DO NOTHING` against the Analysis' unique index) and `reopen` revokes them; `manual` and `parity` are plain. A code the registry does not know is `manual`. The readiness is recomputed with `recomputeReadiness` in the same transaction, and `task.updated` and `migration.updated` are published.
- **Analysis inputs (LIF-021).** Creating or revoking an Expected Difference, including the ones an `accept` task makes, calls `markAnalysesStale` in the same transaction: for the Migration, or for the whole Route when the record is Route-wide. A task status change alone is not an Analysis input, so it does not.
- **Parity (LIF-062, ADR-0396).** After the commit of a task action or of an Expected Difference create or revoke, the endpoint calls `enqueueParity(migrationId)`; it never runs a check inline. A failed enqueue is reported to `onFault` and does not undo the change (the data is stored; the next trigger or drift check covers it). Revoking a Route-wide record enqueues one check per analyzed repository Migration of the Route, at most 500.
- **Expected Differences.** `POST /migrations/{id}/expected-differences` takes `{facetKey, path, note}`: the Facet must be registered and the path a valid path pattern (`parsePathPattern`), else 422; the note is required; an identical active record is 409. `DELETE /expected-differences/{id}` revokes `manual_accepted`, `lossy_accepted`, `overlay` and `unreadable_defaulted` records; `identity_excluded` (lifted with the Identity Mapping, AUTH-050) and `framework_mutation` (bookkeeping of the Run ledger) are 409; an already revoked record is 409. API-020 has no edit endpoint for an Expected Difference; none is added. To change one, revoke it and create another.
- **Audit (AUTH-022).** Every mutation writes an AuditEvent: `run.create`, `run.cancel`, `migration.mark_complete`, `migration.revoke_complete`, `task.done|reopen|dismiss`, `expected_difference.create|revoke`. The typed confirmation of a Run is never recorded.
- **Web (UI-021).** The repositories list offers Migrate on a `ready` row and Run anyway on a `needs_attention` row, hidden while the Migration is `running` or `source_missing`. Each opens a confirmation dialog; Run anyway names the open pre tasks it skips. The server decides again, and a 409 or 422 shows its own text and refreshes the list.

## Round 2 decisions

- **Rollback confirmation (LIF-077) at the single gate.** `checkRunOptions` (called by `createRun`) requires `confirm` equal to the Migration's target full name for every `rollback` Run, compared case-insensitively after trimming (`adoptNonEmpty` stays an exact match, LIF-043). A Migration with no target to name has nothing to confirm. A violation is `run.confirmation_required` (422 `confirmation_required`). No other kind needs a typed confirmation in the spec. The earlier follow-up is closed.
- **Audit in the mutation's transaction (AUTH-022).** `createRun` and `requestRunCancel` take an optional `inTransaction(tx, ...)` hook; `startRun` and the cancel endpoint write `run.create` and `run.cancel` there, including the cancel after a failed enqueue (`reason: enqueue_failed`). A cancel that finds the Run already finished writes nothing.
- **A failed enqueue is a 503 only if the Run ended `cancelled`.** If the cancel finds the Run started by a worker (`requested`), the Run is real and the request is accepted (202).
- **`run_not_permitted` (409)** is a distinct problem code for a lifecycle refusal (`run.not_permitted`, for example a `source_missing` Migration), with its own UI text. A retired Route stays `conflict`.
- **Ownership of `accept` acceptances.** The Expected Difference table has no column for the creating task, and adding one was judged out of proportion. The owner is derived: a migration-scoped `lossy_accepted` row (policy key in `note`) belongs to the done `accept` tasks of the Facet whose `params` list its path. Reopening a task revokes only the paths no other done accept task of the same policy key covers; `DELETE /expected-differences/{id}` is 409 for a row a done task covers. Staleness is marked only when a row was really inserted (the `INSERT` row count) or revoked.
- **Registry is required (503)** for task actions and Expected Difference creation: the completion mode and the Facet check are not skipped when the service is missing.
- **Route-wide revoke fan-out** wraps its Migration lookup in the same fault handling as the enqueue: a failure goes to `onFault` and does not fail the request.
- **Web.** The Run anyway dialog reads its row from the live list by id, so the open-task count is not a snapshot.

## Alternatives

- Reuse `conflict` and `validation_failed` for every Run refusal and put the guard code in `detail`. Rejected: the UI maps `code` to text, and `detail` is machine-facing.
- Leave the Run `queued` when the queue is down and let the orphan sweep re-enqueue it. Rejected: the caller would see success for a Run that may never start while the queue is down; cancelling restores the Migration at once.
- Let `dismiss` apply to a `done` task. Rejected: the task would lose the fact that it was done; the operator reopens it first.
- An edit endpoint for Expected Differences. Rejected: not in API-020; revoke and create keeps a record of each decision.
