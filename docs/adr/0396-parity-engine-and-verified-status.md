# ADR-0396: Parity Check, verifiable tasks and the verified status

- Status: accepted (spec updated)
- Date: 2026-10-09
- Task: T-072
- Affects: LIF-002, LIF-003, LIF-004, LIF-020, LIF-042, LIF-045, LIF-048, LIF-060, LIF-061, LIF-062, LIF-063, LIF-065, LIF-081, JOB-050

## Context

LIF-060 to LIF-063 describe what parity compares and when it runs, but leave open: where it runs in the Run executor, which Migration a check may change and when, how the lifecycle table's "then `parity_*` from the Run's verify step applies" is realised for a Run that finishes after the verify Step, what the system actor of an auto-completed task is, how Overlays reach the desired document, what a Facet is when only one side can be read, and which code the `parity.migration` job (JOB-050) and the callers of LIF-062 use.

## Decision

- **Modules** (`packages/jobs/src/parity/`): `compute.ts` reads, translates, compares and subtracts (no writes); `store.ts` writes ParityResults and completes tasks; `verdict.ts` decides the lifecycle event; `step.ts` is the `verify` Step and the `verify` planner; `run.ts` is parity outside a Run (`runParity`) and the `parity.migration` handler. The Analysis' helpers (`loadIdentityMappings`, `effectiveCaps`, `buildDeployKeyUsage` and others) are exported from `analysis.ts` and reused, so parity translates with the same inputs as the Analysis.
- **Registration.** The worker registers `createVerifyPlanner(parityDeps)` for kind `verify` through `RunStepRegistry.register`. T-071's migrate planners append `createVerifyStep(parityDeps)` as step 13 (key `verify`, severity `advisory`, LIF-040 and LIF-042); it needs nothing from `ctx.services`. The `parity.migration` placeholder of `maintenanceHandlers` is gone; `parityHandlers` replaces it.
- **Per Facet.** The source decides which Facets a Migration has, as in the Analysis: a Facet the source cannot be read for writes no ParityResult; a Facet with `compareMode: none` neither (LIF-060). For the others: source read, LIF-045 source-side filtering (the framework's own source Mutations are removed), `translate` with the current mappings, Overlays merged into `desired` (`mergeOverlay`: objects merge, keyed collections merge by key, everything else is replaced; the overlay wins), `compare`, then the Expected Differences of the Migration and Route that mask (LIF-063; `lossy_accepted`, `unreadable_defaulted` and `overlay` never hide a diff). `identity_excluded` records, including those T-085 creates for deselected invitations, and `manual_accepted` records need no special handling.
- **Failures.** A Facet whose source or target read fails, whose `compare` throws, or whose repository is gone is `unverifiable` (LIF-042). A rate limit (`rate_limited`) or an abort is not: it ends the check and the executor delays the Run (ADR-0341), or the job retries. A translation error makes every compared Facet `unverifiable`.
- **Status `verified`.** LIF-002 says `parity_*` "from the Run's verify step applies" after `run_finished`. `endRunIn` (run/finish.ts), in the transaction that ends a `migrate`, `run_anyway`, `resync` or `verify` Run, applies `parity_equal` or `parity_different` once `run_finished` has been applied, but only when the Run's `verify` Step `succeeded`. A failed Run skips `verify`, so it changes nothing. The event is chosen by `parityVerdict` from the latest ParityResult of every Facet and the open ManualTasks (LIF-061): `parity_different` if any Facet is `different`; `parity_equal` if at least one Facet wrote a result, all are `equal` and no task is `open`; otherwise no event (`unverifiable` is neither). It goes through `transition()`, so LIF-003 decides what is legal (`partial` also becomes `verified`; `verified` and `manually_completed` become `drifted` and keep `statusBeforeDrift`; `drifted` returns to it).
- **Parity outside a Run (LIF-062).** `runParity(deps, migrationId, options)` does the same for a Migration in `migrated`, `partial`, `verified`, `manually_completed` or `drifted` and returns `{skipped}` for the others. A Migration with a Run in flight is left alone (its `verify` Step reports); the status is re-read under the Migration lock after the reads. Callers: the `parity.migration` job (`JobRuntime.enqueueParity`, deduplicated per Migration while waiting), T-074 after a task update, T-085 after an Invitation status change, T-089's drift sweep, an "accept" (LIF-065). The endpoint-scope Migration (LIF-081) is checked the same way over the endpoint Facets; for it a difference on a `verified` Migration is drift (LIF-065).
- **Verifiable tasks (LIF-061, LIF-006).** In the same transaction as the ParityResults, an `open` ManualTask with `verifiable = true` whose Facet reports `isTaskSatisfied(task, target, diffs)` becomes `done` with `completedAt = now`, `completedById = null`, `note = 'parity.auto-completed'`, and an AuditEvent with `actorId = null` (the system) and action `task.auto_complete`. This is evaluated before the verdict. It keeps the invariant of ADR-0310: an Analysis reopens only a `dismissed` task with a null `completedById`, and parity never dismisses; a `done` task stays `done` (LIF-020 step 6). A Facet that is `unverifiable` has no target document, so its tasks stay open. Completing a task recomputes readiness (LIF-004) and publishes `task.updated` (at most 25 per check).
- **Locking.** The store runs under the Migration row lock; inside a Run it runs through `ctx.transaction(..., {migration: true})`, so the order is Migration, then Run, both `FOR NO KEY UPDATE` (ADR-0340). Reads happen before the lock.
- **Events.** `migration.updated` after every stored check, `task.updated` for completed tasks; `run.updated` is the executor's.
- **Ordering of checks (round 2).** Two checks of one Migration can overlap (an on-demand check that reads slowly, a verify Run). `Migration.parityGeneration` (bigint, migration `20261009000020_parity_generation`) is bumped by every stored check. A check reads the generation and the database clock (`checkedAt`, taken before any provider read) when it starts. Under the Migration lock, `storeParity` compares: if the generation moved, the computation is older than what is stored, so nothing is written and no event follows (`runParity` returns `{skipped: 'superseded'}`; the verify Step reports `superseded` in its detail). `writeResult` also never replaces a row whose `checkedAt` is later than the check's own. Without this a stale `equal` overwrote a newer `different` and produced a false `verified`.
- **Rows of Facets the check did not produce** are deleted in the same transaction, so a Facet that is gone cannot decide the verdict with an old result. A check that compares no Facet stores nothing (`no-facets`; the Step is `skipped`).
- **Degraded inputs.** A compared Facet whose transitive `dependsOn` includes a Facet whose source read failed is `unverifiable` (`dependency-unreadable:<facet>`), and so is every Facet when the target lookup returns a repository whose provider id is not the migrated one (`target-missing`).
- **Hand-off notes.** T-073 and T-089: a `verify` after cutover uses containment (ADR-0397), so it reports `verified` even when the target has extra commits; T-089 passes `lfs: 'skip'` when refs did not change.

## Alternatives

- Let the `verify` Step apply `parity_equal` itself: the Migration is `running` then, and the table leaves the event unchanged.
- A system Actor row for `completedById`: the invariant of ADR-0310 and the reopen rule need `null`, and the audit trail has `actorId = null` for the system already.
- Merge Overlays in the Analysis: LIF-048 puts the merge in the Run (`overlays.apply`); parity needs the same merge, which T-071's Step can import from here.
