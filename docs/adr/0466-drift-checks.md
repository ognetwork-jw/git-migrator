# ADR-0466: The drift sweep, drift checks and accepting drift

- Status: agent-decided
- Date: 2026-10-09
- Task: T-089
- Affects: LIF-065, LIF-060, LIF-061, LIF-062, LIF-063, LIF-045, LIF-070, FAC-GIT-005, FAC-GIT-006, JOB-011, JOB-050, API-020, ADP-020

## Context

LIF-065 says drift applies to `verified` and `manually_completed` Migrations, runs on a schedule with FAC-GIT-006 containment once the source is read-only, produces `drifted` with `statusBeforeDrift`, and is resolved by resync, accept or re-mark complete. LIF-060 step 1 says a drift check re-reads the target plus the source `git-refs`, and the full source only when `schedules.driftReadsSource` is true. JOB-050 says `drift.sweep` enqueues `parity.migration` per eligible Migration, spread across the interval. The `drift.sweep` handler was a placeholder (T-028), and follow-ups asked T-089 for containment on top of the strict compare (T-050), `enqueueParity` instead of an inline check and `lfs: 'skip'` when refs are unchanged (T-072).

## Decision

- **The sweep (`drift/sweep.ts`) replaces the placeholder.** It counts and pages the eligible Migrations and calls `JobRuntime.enqueueParity(id, {drift: true, delayMs})` for each; it reads no provider and runs no check. Eligible: a repository Migration that is `verified` or `manually_completed` (the two statuses LIF-065 names), has a target, on a Route that is not retired, whose source repository is present. `drifted` Migrations are not swept: they already carry the verdict, and their resolutions (resync, accept, mark complete) each end in a Parity Check. A `drifted` Migration whose queued drift check runs later is still checked, so that it clears itself when the differences are gone. Endpoint Migrations have their own schedule (`schedules.endpointParity`, JOB-050).
- **Spread.** Delay `i` of `n` is `floor(i * 0.9 * interval / n)`, where `interval` is the time between two firings of `schedules.drift` (cron-parser, UTC, clamped to one minute to one day, one day when the expression cannot be read). Every Migration has its own slot, so a failed enqueue (logged, counted, the sweep goes on) costs only that Migration its check until the next sweep.
- **A drift check is the `parity.migration` job with `drift: true`.** The payload stays IDs only and strict (`drift` is the literal `true` or absent), so a stray field is still refused (JOB-011). It has its own waiting slot (`parity-drift-<id>` against `parity-<id>`): a drift check must never stand in for a check somebody asked for (an accept or a task update, LIF-062), because it reads less. Both go through `enqueueParity`; nothing in the drift path or the API calls `runParity` inline (T-072 follow-up closed, together with the API's existing callers).
- **What a drift check reads (LIF-060 step 1).** The target in full, the source `git-refs` live, and every other source Facet from the source Snapshots of the Migration's **latest Analysis**, unless `schedules.driftReadsSource` is true (then it reads the source as a verify Run does). The Snapshots were read through the same source lock view as any Analysis (ADR-0425), and attachments (pipeline file text) are not needed by any Facet's translation. A Migration with no Analysis, or whose Analysis has no source Snapshots, is read in full. The cost of not re-reading is that a drift check does not see a source change made after the Analysis; every Run and every Analysis refreshes it, and a verify Run or an on-demand check reads the whole source.
- **Drift ignores the source read-only Mutations.** The live source reads go through `sourceLockView` (T-073), so the adapter leaves the framework's restriction and description prefix out by identity (LIF-045), and the Snapshots were taken the same way; a Facet withheld while a lock write is unsettled is `unverifiable`, never `different` (ADR-0425). Integration test: a verified Migration with the source locked stays verified under a drift check of either kind.
- **Containment (T-050 follow-up).** `applyContainment` runs in `compare` for every Parity Check while `sourceReadOnlyApplied` is true (ADR-0397), so a drift check needs nothing on top of the Facet's strict `compare`: an extra target branch or a target ref that descends from the source tip is not drift, a missing source ref or a diverged one is.
- **LFS (T-072 follow-up).** The drift check hashes the `git-refs` document it read from the source (`hashCanonical` of the same JSON-safe form the Analysis hashes) and compares it with the hash of the Analysis' `git-refs` Snapshot. When they are equal the LFS objects the source references cannot have changed and the mirror and batch check are skipped (`refsUnchanged`; the explicit `lfs: 'skip'` option of `ParityOptions` is unchanged for other callers). The residual: an LFS object deleted from the target while the source refs stay the same is found by the next verify Run or on-demand check, not by a drift check.
- **A drift check stamps `Migration.lastDriftCheckAt`** (with `lastParityAt`) in the transaction that stores the result, whatever the outcome. The result is stored and the verdict applied exactly as for an on-demand check (`parity_different` moves `verified` and `manually_completed` to `drifted` and keeps `statusBeforeDrift`; `parity_equal` returns a `drifted` Migration to it; `migration.updated` is the event). A drift check on a Migration that is not `verified`, `manually_completed` or `drifted` is skipped.
- **Accept (`POST /migrations/{id}/drift/accept`, `{note}`, operator).** In one transaction under the Migration lock: only a `drifted` Migration (409 otherwise); for every stored difference of every Facet whose latest ParityResult is `different`, a Migration-scoped `manual_accepted` Expected Difference whose path is `patternForPath(diff.path)` (the only safe way from a concrete path to a pattern: a branch named `release/*` must not become a glob; a path that cannot be a pattern is returned in `skipped` and accepts nothing), unless an identical active one exists (`alreadyAccepted`); one `expected_difference.create` AuditEvent per row (as the single-path endpoint does) and one `migration.drift_accept` event; `markAnalysesStale` (Expected Differences are Analysis inputs, LIF-021); `migration.updated`. After the commit it enqueues a Parity Check (a failed enqueue is a logged fault and does not undo the acceptance), and `parity_equal` then returns the Migration to `statusBeforeDrift`. A ParityResult keeps at most 1,000 differences (ADR-0395): when a Facet stored that many, `truncated` is true and the re-check may drift again until accept is repeated.
- **Resync and mark complete** need nothing new: a resync Run ends `migrated` then `verified` through the verdict of its `verify` Step (LIF-002, integration test), and `mark_complete` from `drifted` was T-074's.

## Alternatives

- Sweep `drifted` Migrations too: re-checks what an operator has not resolved every day, with no new information, and spends provider quota on it.
- Always read the whole source: simplest, but `schedules.driftReadsSource` exists to avoid the source's quota for thousands of Migrations.
- A separate `drift.migration` job: a second processor for the same check and a second deduplication story; the existing job plus a flag is smaller.
- Skip LFS by the stored `lfsBytes`: that is a byte count of the last Run, not a statement about the current refs.

## Round 2 (review findings)

- **A drift check cannot replace the check an Expected Difference change enqueued.** Expected Differences are inputs of a check, and a check that read the old ones and stores later could replace the fresher result (`storeParity` keeps the first check to commit). Every transaction that changes them now moves `Migration.parityGeneration` in the same transaction: drift accept, creating or revoking an Expected Difference (a Route-wide one moves the generation of every Migration of the Route), and a task accept that changes a `lossy_accepted` row. A check that started before is then the one that is superseded and stores nothing. The drift check and an on-demand check keep their own waiting slots (a waiting on-demand request is never dropped for a drift job); the generation, not the queue, orders what is stored.
- **A refs-only check never drops a Facet.** A needed Facet the Analysis has no Snapshot of (it withheld it, or could not read it) is read live together with its dependencies; if it cannot be read it is `unverifiable`, never omitted, so a stored result is neither kept nor deleted by accident. Test: an Analysis without a `deploy-keys` Snapshot, and a target whose keys were removed, drifts.
- The refs-only read does not see source-side settings changes made after the last Analysis; they are seen at the next Analysis or verify Run (`packages/jobs/README.md`).

## Round 3 (review findings)

- **Every writer of an Expected Difference bumps `parityGeneration`.** The helper moved to `@git-migrator/db` (`supersedeParityChecks`). Besides the task accept, create and revoke of ADR-0466 round 2, the mapping exclusions (create, and revoke on reselect, unmap or CSV) and the invitation deselect and reselect bump the Migrations of their Route in the same transaction.
