# ADR-0425: Source read-only Steps (LIF-070)

- Status: agent-decided
- Date: 2026-10-09
- Task: T-073
- Affects: LIF-070, LIF-040, LIF-042, LIF-043, LIF-045, LIF-049, LIF-005, LIF-002, ADP-011, FAC-002

## Context

T-032 built the source adapter's `SourceLock` (apply and undo, ADR-0222) and T-071 the Step framework. LIF-070 and LIF-040 step 14 say what the lock is, but not how the Steps are planned, what the standalone Run kinds contain, how the Mutations are ledgered, what a worker crash in the middle leaves, or what exactly the Analysis filter removes.

## Decision

- **Step 14 is built in.** `source.read-only` is a fixed entry of the migration planner (it needs nothing the worker injects), not an `extraSteps` entry. Severity `independent`: a failure makes the Run `partial` (LIF-042). It is skipped, with a Run log warning when a condition failed, unless all of these hold: the Route's `sourcePostAction` is `read-only` (the Plan only lists the Step then; checked again at run time), the Run option `skipSourceReadOnly` is unset, the source is not already read-only (`sourceReadOnlyApplied`), every Step of 1 to 12 ended `succeeded` or `skipped`, the `verify` Step of this Run succeeded, and the latest `git-refs` ParityResult (checked no earlier than that `verify` Step started) is `equal`. The migration Run ends `migrated`, so the Step sets `sourceReadOnlyApplied` itself; the lifecycle sets it for the standalone kind when that Run succeeds.
- **Two more Run kinds.** `source_read_only` has one fatal Step `source.read-only` without the conditions above (the operator asked for it). LIF-005 gates neither kind by readiness and LIF-070 asks for no typed confirmation, so `createRun` is unchanged apart from the option rule below. `undo_source_read_only` has one fatal Step `source.read-only.undo`. Neither needs an Analysis. `skipSourceReadOnly` is refused with 422 `run.options_invalid` for every kind except `migrate`, `run_anyway` and `resync`, in the single gate `checkRunOptions`.
- **Target web URL.** The adapter contract has no web URL. The URL is the target's git remote URL without credentials, query, trailing slash and `.git` suffix; both supported providers serve the repository page there.
- **Ledger.** Records are written on the `source` side with origin `framework`. Before the adapter call an inert umbrella intent (`resourceRef.kind = source-read-only`, `noop`) is written, the adapter's records follow, then the intent is confirmed `applied`. When the adapter throws, the records it made before failing (`error.mutations`) are ledgered and the intent is confirmed (`applied` if there were records, else `not_applied`). A `possiblyApplied` write fails the Step with the non-retryable `source-read-only.possibly-applied` (ADR-0222: check by hand before running again). Source-side records derive no Expected Difference (ADR-0342); they leave the translation through the filter below, which the Analysis (including the end-of-Run one), the Parity Check and so the drift check all share.
- **Crash between the write and its record: a baseline, never an inference (round 3).** Ownership is never inferred (ADR-0222). Before any write the Step calls `SourceLock.inspect` (optional, read-only: the lock-shaped state on the source as records) and stores what it found in the umbrella intent's `before` as `{baseline: [keys], originals: [records]}` (originals: Round 5), a key being the resource's identity plus the state it shows (so a description is keyed by its text). A resumed Step, or a later lock Run for an intent an earlier Run left open, inspects again and records as NON-inert `create` records flagged `possiblyFramework` ONLY what is not in the baseline and not already in the ledger. State that was in the baseline (a customer's own user-less push restriction on every branch, a description that already had a prefix) is never recorded, so undo cannot touch it. No baseline (an intent without one, or a provider that cannot be inspected): nothing is recorded and the Step fails `source-read-only.needs-manual-check`, telling the operator to inspect the source by hand. When something was recorded the Step also fails with `needs-manual-check`, saying it is recorded and that `undo_source_read_only` removes it. If the baseline cannot be taken, nothing has been written yet and the Step fails. If the source cannot be read when settling, the intent stays OPEN (the error propagates; a retry of the Step, or the next lock or undo Run, looks again against the same baseline) and no message claims a recording. The same path follows a `possiblyApplied` adapter error (`source-read-only.possibly-applied`, with the number recorded). While any lock intent of the Migration is open, `analysis.refresh` is skipped with a warning, because an Analysis then could translate a lock the ledger does not name. `undo_source_read_only` settles open intents first (recording, without failing), so undo reaches the lock.
- **Undo.** `undo_source_read_only` takes the source-side Mutations of the Migration through `mutationsToUndo` and calls `SourceLock.undo` for one Mutation at a time, marking each `undone_at` as soon as the adapter returns. The adapter restores exactly the recorded `before` (the description) or deletes the recorded restriction, and tolerates what is already gone; a description that already equals the original is left alone, so a prefix that was part of the original is never stripped by a repeated undo. After the loop a read-back (`inspect`) must show no lock the ledger does not call adopted; otherwise the Step fails `source-read-only.undo_incomplete` and the flag stays set (the lifecycle clears `sourceReadOnlyApplied` only when the Run succeeds). State the framework only found (adopted) may remain and does not count, and neither does a description equal to what undo restored (the original may itself carry a prefix). Undo also runs when the flag is set and nothing is left to revert, and is not gated by the flag: a half-written lock must stay revertable. T-089's rollback can reuse the Step.
- **What the source reads leave out: identity, not paths (round 2).** LIF-045 says "matched by `resourceRef`". Filtering by canonical path was wrong: the lock contributes to a rule other restrictions share, so removing its paths either erased a user-scoped push restriction on the same canonical pattern (the lock intersects the allow lists to `[]`, and the next resync would delete the target's restriction), hid a later operator edit, or left an empty `**` rule. Now a source read carries `FacetTarget.frameworkResources`: the `resourceRef` of every active (not undone, not `not_applied`) non-inert source-side Mutation of the Migration, adopted ones and `possiblyFramework` ones included (`frameworkSourceResources`). The Bitbucket `branch-rules` driver drops those restriction ids BEFORE `mapBranchRules` combines restrictions, so the rule is exactly what the source holds without the lock. The Analysis (including the end-of-Run one), `computeParity` and so the drift check all read the source this way; `withoutFrameworkCreated` is no longer used for the lock (it stays a pure helper). An adopted lock-shaped restriction is therefore never translated to the target. Lock-shaped state that the baseline (taken before the first lock intent's write) already showed is the customer's own: when apply adopts it, the adopted record is tagged `resourceRef.preexisting` and `frameworkSourceResources` skips it, so it keeps being translated as before and a resync copies the customer's pre-existing freeze to the target, mirroring the source as it was before the framework touched it. Only a lock the framework created, or recovered after the baseline as `possiblyFramework`, is excluded. The tag needs a baseline: with none, adopted state counts as the framework's. The description prefix is still stripped by `normalize` (FAC-SET-003). Consequence: the stored source Snapshot is what the adapter returned, without the framework's resources, not the raw read.

## Alternatives

- `source.read-only` through `MigrationServices.extraSteps`: needs worker wiring for a Step with no dependencies of its own.
- Filtering the lock by canonical path (round 1): see above.
- Failing the resumed Step without recording what is found: leaves a lock that undo cannot reach.
- Failing, rather than skipping, step 14 when parity is not equal: LIF-040 words it as a condition ("Only if ..."), and a failed Step would make every migration of such a repository `partial`.
- Gating undo by `sourceReadOnlyApplied`: leaves a half-applied lock unrevertable.

## Affected requirements

LIF-070, LIF-040, LIF-042, LIF-043, LIF-045, LIF-049, LIF-005, LIF-002, ADP-011, FAC-002.

## Round 2

Review of round 1 (CHANGES_REQUIRED): the path filter erased a user-scoped push restriction on `*`, froze the whole-rule/push-part choice at apply time, and a crash or an unconfirmed write left a lock that undo could not reach and the Analysis translated. Decisions: identity-based filtering at read time (`frameworkResources`), `inspect` to record an unrecorded lock as undoable, undo's read-back before the flag is cleared, only the empty-allow-list restriction counts as visible, and the repeated-undo description fix. The shared-`**` case is covered by adapter tests (a user-scoped restriction survives the lock, a later operator `delete` is visible, removing a co-located restriction leaves no empty rule, a user-less push on `**` the framework did not record is kept) and by an integration test of the unconfirmed write. The fake, like the provider, refuses a second push restriction on `*` itself, so the user-scoped case uses pattern `**` (canonically the same).

## Round 3

The round-2 review found that claiming every lock-shaped thing `inspect` returned could make undo delete a customer's own pre-existing user-less push restriction or prefixed description. Decisions: a baseline taken before the write and kept in the umbrella intent; only what appeared after it is claimed; no baseline means no claim and a manual check; an `inspect` failure leaves the intent open instead of confirming it; the end-of-Run Analysis is skipped while an intent is open; undo's read-back accepts a restored original description that itself carries a prefix; the description key includes its text so a stale adopted record cannot hide a later write; and the adopted-exclusion rule above. Tests: unit (baseline, no baseline, inspect failures, stale intent of an earlier Run, undo settling it, prefixed original) and integration (a crash before the write with a customer's restriction or prefixed description, and a lock over a prefixed original).

## Round 4

The stricter reading of the adopted-exclusion rule: adopted state that was in the baseline is `preexisting` and not excluded (see above; it replaces the round-2 rule that excluded all adopted state). Test: a customer's user-less push restriction on `*`, then a lock Run, then an Analysis still has that rule in the desired target.

## Round 5

The round-3 review (escalated, PROC-008) found that a recovered description record took its `before` from stripping one prefix off the current text, so undo deleted a prefix the customer's original carried; that the Analyses still translated a lock the ledger did not name while a lock intent was unsettled; and that a stale adopted record of the same text hid a later framework write. Decisions:

- **The original comes from the baseline.** `SourceLock` gains `originals(ref)`: the current state of every resource the lock updates in place (the description), whatever its shape. The umbrella intent's `before` is `{baseline: [keys], originals: [records]}`. `inspect(ref, {originals})` sets a recovered description's `before` to the original only when the lock written over it explains the current text (same text once one leading migration prefix is removed from each); otherwise `before` is `null`. Without originals `before` is always `null`. The Step records an in-place `update` only with a non-null `before`; anything else is counted `unrecoverable`, not recorded, and the Step fails `source-read-only.needs-manual-check` (undo: its read-back fails `undo_incomplete`).
- **The write is over exactly the original.** `apply(ref, {targetWebUrl, originals})` refuses to write the description (conflict, nothing written, the restriction already made is still reported) when it no longer shows its original. A write can then only ever be `prefix + original without its prefix`, so the recovered `before` is exact. Without this guard, a change in the seconds between the baseline and the write (for example to another migration prefix over the same text) would be indistinguishable after a crash.
- **Unsettled means blocked.** While a lock intent of the Migration is open: (1) the Step raises the run-origin blocker `branch-rules.source-lock-unsettled` (LIF-049) when it throws with the intent open (a worker that dies resumes the Step, which settles it; any other end is covered by the next point); (2) `createRun` refuses migrate, run_anyway and resync with `run.readiness_required`, through readiness (the blocker) and, in the same gate, by the open intent itself, so a dismissed blocker or a Run ended without the Step's handler cannot let a target write through. `verify`, `rollback`, `source_read_only` and `undo_source_read_only` are not refused: none of them translates the source onto the target (rollback, T-089, is to revert the target's own ledger; a follow-up asks T-089 to keep it that way or gate it here), and the last two are what settles the intent. Settling (recording, or a no-baseline manual check) clears the blocker even when the Step then fails for a check, and both lock Steps list it in `clearsBlockers`. The code's prefix is a Facet key because the closed list of codes (FAC-002 cross-check) accepts only Facet-prefixed codes and LIF-031 lifecycle codes; `source-read-only.unsettled` would be refused, and no existing code fits. It is listed as agent-decided in the cross-check, declared by the `branch-rules` Facet and has guidance.
- **Reads during an unsettled lock.** `sourceLockView` (used by the Analysis, the Parity Check and so the drift check) adds to `frameworkResources` whatever `inspect` shows that the earliest open baseline did not (this changes no ledger and claims no ownership; it only keeps a lock that may be the framework's out of translation). When that cannot be told (no baseline, no `inspect`, or the source cannot be read), `branch-rules` and `repository-settings` are withheld: the Analysis does not read or translate them, and parity marks them `unverifiable` (`source-lock-unsettled`), never `different`.
- **Stale adopted records.** Only undoable records count as already known when recording what appeared (adopted and `preexisting` records are not the framework's writes). Undo's read-back matches an adopted record by the state it showed (`keyOf`), and by identity only when the ledger kept no image (a restriction, whose id names one resource). Keys are canonical JSON (RFC 8785): the database does not keep JSON key order, so a plain `JSON.stringify` of a stored record could differ from the adapter's.
- **`preexisting` needs the ledger too.** An adopted record is tagged `preexisting` only when the baseline showed it AND the ledger does not hold it as the framework's own write. A lock the framework recorded earlier, then found again by a later lock Run, is not the customer's.

### Sweep: why the rule holds

The rule: undo never removes or alters state the framework did not write, and the framework's lock is never translated to the target.

1. **Paths that record a source record with a `before`.**
   - `applyLock`, normal return: the adapter's records. A restriction `create` has `before: null` and names the id the POST returned. The description `update` has `before` = the text read immediately before the PUT, which (with originals) equals the baseline original. Adopted records are inert: undo skips them.
   - `applyLock`, the adapter throws: `error.mutations`, the same records the adapter made before failing (a lost response read back and found applied is recorded with the id or text the read-back saw, `before` as above).
   - `recordAppeared` (resume, a later lock Run, undo's settle, a `possiblyApplied` write): only state absent from the earliest baseline and not already recorded as the framework's write; a restriction by its id; a description only with the baseline original as `before` (see Round 5). A customer's own lock-shaped state was in the baseline and is never recorded. State the customer adds after the baseline while a lock write is unsettled could be recorded as `possiblyFramework`; the Step then always fails `needs-manual-check`, telling the operator what was recorded before any undo runs. That window is closed in practice by the blocker above.
   - Nothing else writes source records (`tagged` only adds `preexisting` to adopted records; undo marks `undone_at`).
2. **Paths that decide something is the framework's.**
   - The adapter's `create` after its own POST (the id it returned) and its `update` after its own PUT: written by the framework.
   - `recordAppeared`: appeared after the baseline that was taken before the first write of the open intent. Undo of such a record deletes the restriction by id or restores the baseline original; a description changed beyond the framework's write is not recorded.
   - `tagged` / `preexisting`: never claims; it only stops adopted customer state from being excluded.
   - `frameworkSourceResources` and `sourceLockView`: decide exclusion from translation, never undo. Their error direction is to exclude (or withhold) a lock-shaped resource that might be the customer's while the state is unknown, never to translate one that might be the framework's.
   - Undo's read-back: adopted state matched by its state is not counted as remaining; everything else keeps the flag set. It writes nothing.
3. **Paths that feed source state into translation or parity.**
   - `runAnalysis` (inline before a Run, scheduled, and the end-of-Run `analysis.refresh`, which is skipped anyway while an intent is open) and `computeParity` (the `verify` Step, the Parity Check and the drift check): both read the source through `sourceLockView`. The framework's recorded lock (creates, `possiblyFramework` records, adopted non-preexisting records) is dropped by id before `mapBranchRules` combines restrictions. An unrecorded lock is either added from `inspect` or its Facets are withheld. The description prefix is removed by `normalize` (FAC-SET-003) for every read.
   - Target writes use the Run's inline Analysis (`createRun` never carries an older one), and are refused while an intent is open, so no translation of an unknown source state reaches the target.
   - No other code path reads a source Facet for translation (inventory reads repository metadata only).

Tests: adapter (`originals`, the guarded write, `inspect` with and without originals, reviewer probe 2 as a permanent test), unit (recovered description with and without an original, the blocker and the `createRun` refusal with the blocker dismissed, `sourceLockView` withholding and adding, relock-after-undo with the same text, the read-back keyed by text) and integration (a crash after the writes over a prefixed original, undone exactly; an unconfirmed and uninspectable write that blocks a resync, is unverifiable in parity, is not translated by a scheduled Analysis, and after a lock Run settles it, a resync that never puts a rule for every branch on the target, then undo back to the original).
