# ADR-0136: devenv CI pins the CLI to a tag; devenv.lock is not committed yet

- Status: accepted (no spec change needed)
- Date: 2026-10-08

## Context

DEP-060 asks for `devenv.yml` with `cachix/install-nix-action` and devenv. The T-093 brief asked for a committed `devenv.lock` if one can be generated. In the implementation session, `github.com` tarballs, `api.github.com` for the `cachix/devenv-nixpkgs` and `cachix/git-hooks.nix` inputs, and `devenv.cachix.org` were refused by the egress policy. A lock needs the exact revisions of those inputs, so one cannot be generated here.

ADR-0066 verified devenv 2.4.0 and recorded that version. It did not pin the CLI for CI, and its Known limits section says the real lock is generated by a maintainer in the T-093 change.

## Decision

1. The CLI is pinned: `nix profile install github:cachix/devenv/v2.4.0`. The tag is the one ADR-0066 used as an override input. The job then runs `devenv version` and fails unless it reports `devenv 2.4.0`, optionally followed by a `+<commit>` build suffix (the first CI run reported `devenv 2.4.0+b904dcb (x86_64-linux)`). `2.4.01` and `2.4.1` are rejected. A test asserts that the install names a tag or a 40-hex revision.
2. No `devenv.lock` is committed in this change. A fake or hand-written lock would pin the wrong inputs.
3. **This overrides ADR-0066's plan and the follow-up row.** ADR-0066 says a maintainer generates the real lock in the T-093 change. That did not happen here, so the lock stays open as a follow-up. The follow-up row in `docs/followups.md` stays open until a maintainer commits a lock.
4. **Unlocked-input risk.** Until the lock exists, `devenv-nixpkgs/rolling` and `git-hooks.nix` float. Each CI run can resolve different revisions of the Nix inputs, so a passing run does not prove the same environment as the last one. The job uses the lock once a maintainer commits one; the lock file is then the pin.
5. `devenv test` runs as a non-root user. The job fails early if `id -u` is 0.
6. **Binary cache.** The first PR run (run 37777214419) built devenv and the Rust toolchain from source and ran out of disk. Without the cache, the build is the cause, so the job now uses devenv's cache in two ways:
   - `nix profile install --accept-flake-config github:cachix/devenv/v2.4.0`, so the tagged flake's own `nixConfig` applies.
   - `extra-substituters` and `extra-trusted-public-keys` in the install-nix-action `extra_nix_config`, so the Nix daemon trusts the cache for every user. The values are copied from the tagged flake: `https://raw.githubusercontent.com/cachix/devenv/v2.4.0/flake.nix`, the `nixConfig` block (fetched in this change). They are `https://devenv.cachix.org https://cachix.cachix.org` and `devenv.cachix.org-1:w1cLUi8dv3hnoSPGAuibQv+f9TZLr6cv/Hm9XgU50cw=` plus `cachix.cachix.org-1:eWNHQldwUO7G2VkjpnjDbWwy4KQ/HNxht7H4SSoMckM=`. No key is written from memory.
7. **Disk.** A step before Nix install removes `/usr/share/dotnet`, `/usr/local/lib/android`, `/opt/ghc` and `/opt/hostedtoolcache/CodeQL`, and prints `df -h` before and after. This is defence in depth for a cache miss.

## Alternatives

- Pin the nixpkgs revision for the CLI instead of the GitHub tag: rejected for now. A 40-hex nixpkgs revision carrying 2.4.0 could not be confirmed from here.
- Commit a generated lock: rejected. The lock could not be generated.
- Configure the devenv binary cache by hand with a key from memory: rejected. The key comes from the tagged flake's `nixConfig` (decision 6).

## Unverified

- The tag `github:cachix/devenv/v2.4.0` was not fetched from here. ADR-0066 used the same tag as an override input, which is the only evidence. CI on the PR will confirm.
- Whether the cache serves every store path the job needs (the rebuild that ran out of disk is expected to be a substitution now). CI run on this PR is the check.
- The version line on the runner. The sandbox printed `devenv 2.4.0 (x86_64-linux)`; the runner printed `devenv 2.4.0+b904dcb (x86_64-linux)`. Both match the check.

## Follow-ups

- A maintainer commits `devenv.lock` from a machine that can reach the inputs. Then the lock is used as the pin.
- Confirm from the run log that the cache serves the build (decision 6). If it does not, record the missing store paths here.

## Affected requirements

DEV-001 (devenv and Compose both first-class; CI exercises devenv), DEP-060 (`devenv.yml`).
