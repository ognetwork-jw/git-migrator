# ADR-0122: Access policy decisions

- Status: accepted (spec updated)
- Date: 2026-10-08
- Task: T-010
- Affects: DOM-005, DOM-011, API-012, AUTH-020, AUTH-021

## Context

AUTH-020 and API-012 give a role table and an RPC write allow-list. Implementing them in ZModel needed these choices.

## Decision

1. **Roles.** `viewer < operator < admin`. A policy reads `auth().role in [operator, admin]` or `auth().role == admin`. `auth()` is `Actor` (`@@auth`). Every `@@allow` also requires `auth().disabled == false` (defence in depth: a disabled Actor reads and writes nothing). A disabled Actor's sessions and API keys are rejected before the RPC mount (AUTH-005, AUTH-040), which stays the primary control.
2. **Reads.** Every model has `@@allow('read', auth() != null)`. An unauthenticated client (`forActor(undefined)`) reads no rows and writes nothing. It returns empty results rather than throwing, which is how ZenStack filters; the 401 for unauthenticated requests belongs to the API layer (AUTH-020).
3. **Default-deny writes (DOM-005).** No model has an `@@allow` for create, update or delete except those of API-012: `Wave` (operator+), `NamingRule`, `WebhookAllowlistEntry`, `Overlay` (admin), `Migration` update (operator+) and `ManualTask` update (operator+). Those last two are narrowed to one field each by field-level `@deny('update', true)` on every other scalar field (`waveId` and `note` are the exceptions). `createdAt` and `updatedAt` are denied too: an operator must not rewrite timestamps through RPC, directly or through a nested `wave.update({ migrations: { updateMany } })`. A new `Migration` or `ManualTask` field is therefore denied until someone deliberately opens it, and `policy.test.ts` fails if a scalar field lacks the `@deny`.
4. **Relation fields cannot carry field policies** in ZenStack ("Field-level policies are not allowed for relation fields"). The foreign-key scalar's `@deny` is what stops `data: { route: { connect } }`; the tests prove it for `Migration.route`, `latestAnalysis` and `ManualTask.completedBy`. `Migration.wave` and its `waveId` stay open. Nested creates through an allowed model (`wave.update({ migrations: { create } })`) are refused by the child model's create policy.
5. **API key hash.** API-012 says the hash is "denied for read to roles below their AUTH-020 row", but AUTH-020 grants no row at all the right to read a hash ("Read everything except API key hashes"). `ApiKey.hash` is `@deny('read', true)` for **every** role, admin included. Key verification (AUTH-040) reads it with the privileged client. A denied field reads as `null`, and a `where` on it matches nothing, so the hash cannot be probed.
6. **Raw response bodies.** `RawResponse.body` is `@deny('read', auth().role == viewer)`; operators and admins read it (AUTH-020 "Read raw responses"). The metadata (method, URL, status) stays readable to everyone.
7. **updated_at is set by a database trigger** on `Migration` and `ManualTask`, not by `@updatedAt`: the ORM writes an `@updatedAt` column in every update, and the field-level `@deny` on it would then reject the allowed `waveId` and `note` updates (tested). The columns default to `now()`, and `app.set_updated_at()` triggers set them on every UPDATE, including privileged ones.
8. **Deleting a Wave** reaches `Migration.waveId` through the database `ON DELETE SET NULL` (DOM-013), not through a policy-checked update, so an operator who may delete a Wave need not be able to update lifecycle fields.
9. **Privileged client and the `forActor` facade** (amended by ADR-0200: arguments are validated and deep-cloned, not just walked). `createDb().privileged` is a `ZenStackClient` without the policy plugin; `forActor(actor)` derives a policy-enforcing client from the same pool. Only the latter may be given to the RPC mount (T-021). What `forActor` returns is not a ZenStack client but a frozen object with a null prototype. It is an allow-list of three kinds of member:
    - The model delegates, as frozen copies. Each call returns an opaque frozen thenable whose only own keys are `then`, `catch` and `finally`. The real ZenStack promise, which carries the `cb` that runs with the full transaction client, is held in a module-level WeakMap together with the client that issued it.
    - `$transaction`. A callback runs with the same facade over the transaction client. An array is accepted because the ZenStack RPC transaction route calls `client.$transaction([...])` (checked in `@zenstackhq/server` 3.9.7), but every element must be a thenable that this very facade issued. Otherwise the whole call is rejected before anything runs. A forged `{ then, cb }` object is therefore refused and its `cb`, which would receive a client with no policies, never runs. Anything that is neither a function nor an array is rejected too.
    - Delegate arguments are data only. ZenStack accepts a function under `where.$expr` and calls it with the Kysely expression builder, which gives a viewer raw SQL (`query_to_xml`, `pg_advisory_lock`) beneath the policy plugin. Before a delegate runs, the facade walks its arguments and accepts plain objects and arrays, primitives (string, number, boolean, null, undefined, bigint), `Date`, `Decimal` and `Uint8Array`. It refuses a function, any other object (class instance, Map, Set), a key named `$expr` (whatever its value), symbol keys, accessor properties, cycles and nesting deeper than 64 levels, at any depth, so `include`, `select` and relation filters are covered. The refusal is an `ORMError` with reason `invalid-input` (RPC status 422), raised before any SQL runs, and has the same shape as the transaction refusal.
    - Errors are sanitized. An ORM error carries `sql`, `sqlParams`, `dbErrorMessage` and a `cause`; logging it would put query parameters in the log. Errors from a delegate or `$transaction` are rethrown as a fresh `ORMError` with the same `reason`, `model`, `rejectedByPolicyReason` and `dbErrorCode` and a generic message (input errors keep their message, which describes the caller's own input). `RPCApiHandler` chooses 403, 404, 422 or 400 from `reason`, so its status codes are unchanged. Errors that are not ORM errors pass through.
    - `$schema`, read-only. `RPCApiHandler` reads `client.$schema.models` to validate model names, so a facade without it cannot be mounted. It is a deep-frozen copy built once and shared by all facades, so a holder cannot edit the policy definitions in the schema that the real clients use. `$procs` stays absent; the handler reads it optionally.

    The first design, a Proxy that threw on a deny-list of members, was bypassed through `$qbRaw`, `kyselyRaw`, `withExecutor` and the property descriptors: the client has too many members beneath the policy plugin for a deny-list to keep up. With the allow-list, `$qb`, `$qbRaw`, `kysely`, `kyselyRaw`, `kyselyProps`, `options`, `$options`, `withExecutor`, `$procs`, `$diagnostics`, `$use`, `$unuse*`, `$setAuth`, `$auth`, `$executeRaw*` and `$queryRaw*` are simply absent. `packages/db/src/rpc.test.ts` drives `RPCApiHandler` with `forActor` clients (viewer read, operator write, viewer write denied, transaction route); `@zenstackhq/server` is a devDependency of `@git-migrator/db` for that.

## Alternatives

- A field-level `@allow` instead of `@deny` on everything else: ZenStack's field `@allow` is for opening fields to an otherwise denied model, not for narrowing an allowed one.
- `$transaction` accepting only a callback: simplest, but the RPC transaction route uses the array form, so the facade could not serve it.
- A deny-list Proxy over the real client: bypassed repeatedly (see item 9).
- Wrapping the expression builder instead of refusing functions: its surface (`fn`, `raw`, sub-selects) is too large to allow-list.
- Handing out the live `schema` object: a holder could mutate the definitions shared by every client.
