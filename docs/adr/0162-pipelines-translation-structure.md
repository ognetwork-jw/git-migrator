# ADR-0162: shape of the generated workflows

- Status: accepted (spec updated)
- Date: 2026-10-08
- Task: T-057
- Affects: FAC-PIP-002, FAC-PIP-003

## Context

FAC-PIP-002 lists the constructs but not the file layout, the job naming, how pipelines that exclude each other in the source stay exclusive, or the mapping details of caches, artifacts and services.

## Decision

- **One workflow per pipeline**, under `.github/workflows/`: `ci.yml` (default), `branch-<slug>.yml`, `tag-<slug>.yml`, `custom-<slug>.yml`. The slug lowercases the key and joins runs of other characters with `-` (max 48); a collision gets `-2`, `-3`. The workflow `name:` is `Default`, `Branch <glob>`, `Tag <glob>`, `Custom <name>`.
- **Default excludes the branches that have their own pipeline.** In the source a branch that matches a `branches` pattern runs that pipeline instead of the default. The default workflow therefore lists `branches: ['**', '!<glob>', …]`.
- **Overlapping patterns.** Within `branches`, and within `tags`, a workflow for pattern `g` excludes (`!h`) every sibling `h` that is strictly more specific, i.e. every ref matching `h` also matches `g` (a literal matched by `g`, `**`, a trailing `/**` prefix). Disjoint patterns (different literal prefixes, or a literal not matched) need nothing. When two wildcard patterns overlap and neither contains the other (`feat*` and `*fix`) the choice cannot be made here, so both paths are listed as unsupported with the reason; the workflows are still generated for review.
- **One job per step**, ids `step-1`, `step-2`, … in source order, counting only generated steps. A stage of one step needs the previous stage; a `parallel` group (list form, or `steps:` form; `fail-fast` is unsupported) shares the previous stage as `needs`, and the next step needs every job of the group. Jobs run on `ubuntu-latest`.
- **One `run:` step per step script** (entries joined with newlines), so `cd` and `export` carry over between entries as they do in the source; `after-script` is a separate step with `if: always()` after the artifact upload.
- **Job order of steps**: checkout, cache restores, artifact downloads, script, artifact upload, after-script.
- **Caches**: predefined paths and lockfile globs are in `constants.ts` (`node` caches `node_modules`, `pip` `~/.cache/pip`, `maven` `~/.m2/repository`, `gradle` `~/.gradle/caches`, `composer` `~/.composer/cache`, `dotnetcore` `~/.nuget/packages`); `docker` is dropped without an unsupported entry. A custom cache without `key.files` uses a generic lockfile set (`DEFAULT_LOCKFILES`). Key: `${{ runner.os }}-<name>-${{ hashFiles(…) }}`.
- **Artifacts**: uploaded as `artifact-<job id>` with `if-no-files-found: error`; every later job downloads the artifacts of all earlier jobs that produced any. The source silently succeeds when nothing matches, the target fails the producing job. `download: false` is unsupported. Upload-artifact v4 roots multi-path uploads at the least common ancestor, so directory layout can differ from the source when globs have different parents; reviewers should check it.
- **Services**: only `image` and `variables` are translated, with literal values or whole `$NAME` references to known variables. For a few well-known database images the standard port is published (`SERVICE_PORTS`), because a job on the runner reaches a service through `localhost` only with a published port; a job with a `container:` gets none (it reaches the service by name, unlike the source).
- **`definitions.steps`** only holds anchors (resolved before translation) and is not reported. Any other unknown `definitions` key, top-level key (`options`, `clone`), pipeline key (`pull-requests`) and step key is reported at its path.
- **Header and TODO comments.** Each workflow starts with `# Generated by git-migrator from bitbucket-pipelines.yml (<pipeline path>). Review it before merging.` and one `# TODO(git-migrator): <path> — <reason>` line for each unsupported path under its pipeline; paths that belong to no workflow (top-level, `pull-requests`) go into the first workflow in file-name order.

## Alternatives

- One workflow for the whole file with `if:` conditions per ref: harder to review and to compare by path (FAC-PIP-004 compares workflow paths).
- One `run:` step per script entry: loses shell state between entries.
- Exact artifact paths via an archive step: adds constructs beyond the spec.
- **Assumption on pattern selection (unconfirmed).** Neither the spec nor the provider docs state whether a ref that matches several patterns runs the most specific pipeline or the first in file order. The translation assumes specificity (the exclusions above) and, for every overlapping pair whose file order disagrees with specificity (the broader pattern is listed first), reports both paths in `translation.unsupported` with a reason that the source may resolve the overlap by file order. The reviewer of the Change Request confirms the intent. The note is repeated in `docs/providers/bitbucket-cloud.md`.
- **Unknown relations are always reported.** A pair of wildcard patterns whose relation is `unknown` is listed whatever the file order. Pattern order is read from the YAML document, because `Object.keys` puts integer-like keys such as `'2024'` first; if the document order cannot be read, integer-like keys are compared against covering patterns as if either order were possible.
