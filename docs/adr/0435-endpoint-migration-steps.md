# ADR-0435: Endpoint migration Steps, team settlement and the endpoint pages

- Status: accepted (spec updated)
- Date: 2026-10-09
- Task: T-086
- Affects: LIF-080, LIF-081, UI-025, UI-026, FAC-ACL-004, AUTH-050, AUTH-060, AUTH-061, ADP-012, LIF-077

## Context

T-071 left endpoint-scope Runs failing with `run.scope_unsupported` (ADR-0380) and asked T-086 to register the endpoint Steps through the planner's scope dispatch. The spec gives the order (LIF-081: `members`, `teams`, `org-variables`, `org-webhooks`, `verify`) and says that when the endpoint Migration creates a team the GroupMapping becomes `confirmed` with `targetGroupId` set (AUTH-050). It is silent on how that happens, on how the repository Migrations learn of it, on what a mapped group's slug is in the Teams Facet, and on the pages' data sources.

## Decision

- **Same planner, scope dispatch.** `createMigrationPlanner` returns `endpointSteps` for an endpoint Migration: the `step` PlanItems of the Run's Analysis in the order `ENDPOINT_STEP_TEMPLATE` gave them, each `facet.<key>.apply` for `members`, `teams`, `org-variables` and `org-webhooks` mapped to `endpointFacetStep(key)`, `verify` taken from `MigrationServices.extraSteps`, and the closing `analysis.refresh`. The executor and the three Run kinds are unchanged. A Run without an Analysis plans the fatal Step `run.analysis_missing`.
- **Facet Steps share the ledger path.** `endpointFacetStep` reads the target organization, recovers open intents of a resumed Step, and writes through `applyWithLedger` (umbrella intent, every driver record ledgered as it arrives, confirm), over the quota-aware client of `connectSide`. It targets `{scope: 'endpoint', namespace}` of the Route's target namespace. All four Steps are `independent`: a failed `org-webhooks` leaves the teams in place and the Run `partial`.
- **`members` writes nothing.** The Plan lists a Step only for a Facet the target can write, and the target's `members` driver has no `apply` (AUTH-061: people are invited only through approved Invitation Batches, ADR-0370). The Run order of LIF-081 is kept by the Plan; no code path in the endpoint Run can invite.
- **Membership respects invitations.** The Run applies the `desired` document of its own Analysis. The Teams Facet already leaves out principals that are not in `targetOrgMembers` (so a person with an outstanding invitation, who is not yet a member, is left out), `pending_invite` and excluded principals, and the target driver checks organization membership again when it writes (a membership write would otherwise invite). A person joins their teams in the first endpoint Run after the invitation is accepted and the mapping is confirmed (ADR-0370, per target organization).
- **Settling teams.** After `facet.teams.apply`, `settleTeams` finds the teams this Migration created from the ledger (`Mutation` rows of `teams`, `create`, not undone, `recorded`; by `resourceRef.slug` or the path `/teams[slug=x]`, so a record recovered after a crash counts), lists the target organization's teams through the inventory interface, upserts the target `Group` rows, and moves the Route's GroupMappings whose `plannedSlug` equals a created team's slug and whose status is `unmapped` or `suggested` to `confirmed` with `targetGroupId`, under the Route mapping lock (`identity-mapping:<routeId>`, ADR-0320). A team the framework did not create is never confirmed here: AUTH-050 keeps that an operator's decision. If a created team is not listed yet, the mappings are left alone and the next inventory or Run settles them.
- **`access-control.team-missing` clears by re-Analysis.** The blocker belongs to the repository Migrations, not to the endpoint Migration, so no `clearsBlockers` applies. `settleTeams` marks the Analyses of the Route's repository Migrations stale (`markAnalysesStale`, ADR-0310) and publishes `migration.updated` for them; the feeder (JOB-020) or an operator analyzes them again, the group principal now resolves (`mapped`), and the blocker is gone. The endpoint Migration's own Analysis is refreshed by the Run's last Step.
- **Spec gap: the Teams Facet slug of a mapped group.** `plannedSlug` returned the resolver's principal id for a mapped group, which assumed that a group principal's id is a slug. The target's group principal is the provider's team id (what `access-control` writes and what `Group.providerId` holds), so once a mapping was confirmed the next Analysis planned a team named after the id and the endpoint Run created it (the integration test caught this). The route index gains `targetSlugs` (source group id to the slug of the confirmed target Group), and `plannedSlug` uses it for a mapped group, falling back to the principal id when the index has none. Teams stay keyed by slug; `access-control` keeps the id.
- **Re-runs change nothing.** A second Run finds the team and its members and writes nothing (integration test), because the desired document is derived from the confirmed mapping's real slug.
- **Rollback.** Team and membership creates are ledgered `create` records, so a rollback Run undoes them (LIF-077). Returning a GroupMapping to `unmapped` when its team is undone belongs to the rollback task (T-075); reported as a follow-up.
- **Pages.** UI-025 (`/endpoints`) and UI-026 (`/endpoints/routes/[routeId]/migration`) read the Model API (`endpoint`, `route`, counts of `repository`, `identity` and `group`, the latest `repository.lastInventoriedAt`, `migration`, `planItem`, `run`), `GET /api/v1/dashboard` and `GET /api/v1/migrations/{id}/diff`, and are live through `useLiveTopics` (`list:repositories`, `list:migrations`, `migration:<id>`, `list:runs`). Actions use `POST /migrations/{id}/analyze` and `POST /migrations/{id}/runs` with `{kind}` (T-074): the Run button offers `migrate` when readiness is `ready` and `run_anyway` when it needs attention, and the server re-checks (LIF-005). Both pages gate on `/endpoints` (`read`); actions need `operate`. The layout follows UI-022 (header, Overview, Facets, Runs). Guidance rendering for findings joins with UI-040 (T-087); until then findings show their code, Facet and field paths.

## Alternatives

- A second planner or executor for endpoint Runs: duplicates ordering, retry and ledger code (ADR-0380 said not to fork it).
- Confirming the mapping from the next target inventory: the inventory only ever suggests (AUTH-050), and waiting for it leaves repositories blocked between the Run and the inventory.
- Clearing the blocker with `clearsBlockers`: it is not a run-origin blocker of the endpoint Migration.
- Making the resolver return the slug for groups: `access-control` needs the id, and one resolver cannot serve both.

## Affected requirements

LIF-080, LIF-081, UI-025, UI-026, FAC-ACL-004, AUTH-050, AUTH-061.

## Round 2 (review of PR 51)

- **One lock, one hash.** The mapping and invitation endpoints, the invitation jobs and `settleTeams` all take transaction advisory locks through `advisoryXactLock` and the key builders `routeMappingLockKey` and `invitationTargetLockKey` (`@git-migrator/db`, `locks.ts`). `settleTeams` runs in one transaction that takes the target Endpoint's invitation lock, then the Route mapping lock (ADR-0370 order), then the rows. It no longer uses `withSessionLock`; that helper (a session lock for provider calls, `target-name:<endpoint>:<name>`) is untouched, because nothing else takes that key.
- **Crash recovery counts.** A team is ours when the ledger holds a `create` record of it, or a `recovered-write` of the teams Facet (ADR-0380 round 2) in which the team is absent from the umbrella `before` and present in what was read back (recovery only records paths the write meant to make). A same-slug team with no such proof is never confirmed.
- **No credentials in the ledger.** The umbrella intent's `meant`, `before` and `after`, and the `after` of a recovered record, pass through `ledgerSafe`: for `webhooks` (repository, from T-071) and `org-webhooks`, URLs are reduced to their origin. Recovery redacts the fresh read the same way before diffing; hooks are keyed by `key`, so the URL is not needed to tell what changed. No other Facet's document holds secret values.
- **Ambiguity is not guessed.** A created team is confirmed to a mapping only if exactly one `unmapped`/`suggested` mapping (or `confirmed` mapping whose team is gone) plans its slug and no confirmed mapping already holds the team; otherwise a `teams.unmapped-principal` pre task (principal `group:<slug>`) asks for a decision. The update is conditional on the status read under the lock, so a decision made meanwhile survives.
- **Renamed or deleted team.** In the endpoint Analysis a `confirmed` mapping whose target team is not among the live teams counts as `team_missing` (`liveGroupRows`), so the Plan creates the team under its planned slug (visible as a create in the Facet diff) and the Run points the mapping at it. No separate finding code was added: the diff shows it, and the repository Migrations report `team-missing` as soon as their mapping resolves again.
- **No silent drops.** A Step the Plan lists with no implementation (for example `source.read-only` before T-073) is planned as a skipped advisory Step with its reason and a Run log warning (`unimplementedStep`). `verify` is registered by the worker and runs for the endpoint Run (integration test).
- **Pages.** UI-026 shows the Endpoints' display names and a Facet badge strip (the repository strip component, fed by the Analysis's Steps and findings); finding guidance rendering joins with T-082's reusable component. The page uses T-074's `analyzeMigration` and `startMigrationRun`.

## Round 3 (second review of PR 51)

- **Webhook `key` stays.** `ledgerSafe` no longer runs the generic key-based redaction on webhook documents (it hid the hook `key`, so every hook collided on `[REDACTED]` and recovery could not tell hooks apart). It reduces only `hooks[].url` with `redactWebhookUrl`; the `key` (`<origin>#<hash16>`) holds no secret. Replaces the Round 2 wording above.
- **Liveness is by `Group.providerId`, not slug.** `liveTargetTeams` lists the target's teams once per Analysis (skipped when no confirmed mapping names a team) and `liveGroupRows` uses it in both the endpoint and the repository Analysis. A team live under another slug keeps its mapping and the Analysis uses the live slug (`routeIndex.targetSlugs` too), so a rename plans no duplicate team. A provider id that is gone means the team was deleted: the mapping counts as unmapped, so the Plan recreates the team and a repository Analysis raises `access-control.team-missing` (FAC-ACL-004). No new finding code (the spec's list is closed, FAC-002).
- **`settleTeams`.** It refreshes `Group.slug` and `name` of every live team (rename). It repoints a `confirmed` mapping only when the old team's provider id is no longer live, with the update conditional on the status and the target read under the lock. Every confirmation writes a `group-mapping.confirm` audit event in the same transaction (`actorId` null, `origin: 'run'`, the Run id, the old and new team on a repoint). A repoint also raises a `teams.unmapped-principal` post task whose `principal` text names the old and new team; an ambiguous slug raises the pre task. Tasks are created inside the transaction (`addRunTask`), so a retry cannot lose them.
- **Transaction time.** The ZenStack client has no interactive-transaction timeout option, so nothing cuts the transaction at 5 s; `lock_timeout` (15 s) and `statement_timeout` (60 s) set inside it bound the wait and the work.
- **Recovered writes** count a team only for the `paths` recovery recorded (`/teams[slug=x]`), as for a create, so a foreign team created in the same window is not claimed.

## Round 4 (third review of PR 51)

- **A recovered team is ours only on proof.** A `recovered-write` of the teams Facet counts a team as created when its recorded paths include `/teams[slug=x]/slug` or `/teams[slug=x]/name` (a diff only has those for a whole new element) and `x` is absent from the umbrella `before` and present in the recovered `after`. A member-only change to a team that was already there records only `/members` paths, so it is never claimed. The test builds its paths with `diffDocuments`.
- **Lease fence.** `settleTeams` has to take the invitation and Route locks before anything else (ADR-0370), so it cannot use `ctx.transaction` (that locks the Run row first, the opposite order to the mapping API's lock then Migration row). `StepContext.assertLease(tx)` is new: after the advisory locks it share-locks the Run row `WHERE lease_owner = <token>` and throws `RunLeaseLostError` otherwise, so a worker that waited for the locks and lost its lease writes nothing. Run log lines are written after the commit, because the log write needs the Run row.
- **Shorter lock hold.** The slug/name refresh reads the stored Groups of the live teams in one query and writes only the rows that differ.
- **No repoint task.** The post task is dropped (it reused a `pre` code whose guidance says "confirm the mapping"). A repoint is recorded by its audit event (old and new team), a Run log warning and the Facet diff. The ambiguous-slug `pre` task stays.
